# Встроенная панель администратора

Панель открывается по адресу `/admin` после обычного входа через Keycloak. В локальной среде:
<http://localhost:3000/admin>. Для доступа нужна realm-роль `sozhiteli-admin` в access token. Роль не
включена в роли по умолчанию, регистрация пользователя её не выдаёт. Каждый backend самостоятельно
проверяет подпись, issuer, audience и роль; скрытая ссылка в интерфейсе не заменяет эту проверку.

## Локальный администратор

При уже запущенной инфраструктуре выполните из корня проекта:

```powershell
node tools/admin-setup.mjs
docker compose -f deploy/compose/compose.yaml up -d --build --wait profile
```

Скрипт создаёт отдельную учётную запись `adminlocal@example.test` со случайным паролем. Реквизиты
сохраняются в `research/local-admin.txt`; пароль не выводится в терминал. Каталог `research/` и локальный
`deploy/compose/.env` исключены из Git. На системах с POSIX-правами секретные файлы получают режим `600`.

Откройте этот файл локально и войдите в приложение под указанной учётной записью. Если вы уже вошли под
другим пользователем, сначала выйдите. После назначения или отзыва роли нужен новый access token:
надёжнее выйти и войти заново. Существующие токены живут до пяти минут.

Повторный запуск дополняет существующий realm, сохраняет пароль администратора и секрет серверного
клиента. Данные и Docker volumes сохраняются. Аккаунту с таким же именем, созданному без служебной метки
инструмента, скрипт не выдаёт права. Метку может изменять только администратор Keycloak. Если файл с
паролем утрачен, скрипт не сбрасывает пароль существующего аккаунта: задайте новый через локальную
консоль Keycloak и сохраните его самостоятельно.

Скрипт работает только с `http://localhost:8081`, читает только `deploy/compose/.env` и перед изменениями
проверяет наличие включённого локального клиента `sozhiteli-dev-cli`. Он не принимает адрес production
сервера и не создаёт тестового администратора в production.

После обновления и запуска сервисов выполните `npm run admin:smoke` (или `node tools/admin-smoke.mjs`).
Это сквозная проверка прав, ответов API, списка таблиц, постраничной загрузки и скрытых значений контактов.
Она читает существующие данные, не создаёт анкеты или другие тестовые строки и не выводит реквизиты или
записи пользователей. Для неё нужны сохранённые локальные реквизиты администратора и стандартный
тестовый аккаунт Alice из dev realm.

## Что доступно

В панели есть обзор состояния сервисов, список пользователей с поиском и страницы данных трёх баз.
Список пользователей приходит из Keycloak, поэтому включает зарегистрированные аккаунты без анкеты.
Он возвращает идентификатор, имя входа, email, признаки активности/подтверждения email и дату создания.
Пароли, токены, пользовательские атрибуты и credentials не возвращаются.

| Сервис / база                | Разрешённые таблицы                         |
| ---------------------------- | ------------------------------------------- |
| Profile / profile_db         | `profile`, `city`, `profile_deletion`        |
| Matching / matching_db       | `candidate`, `candidate_view`, `sync_state`  |
| Interaction / interaction_db | `contact_request`, `contact`                |

Показаны размер базы, число строк, имена разрешённых колонок и строки с постраничной загрузкой.
В `contact` видны только `user_id`, `kind`, `updated_at`: сами значения контактов скрыты. SQL-запросы
заданы в исходниках, имя таблицы выбирается из фиксированного списка. Панель не выполняет произвольный
SQL. Системные таблицы, credentials Keycloak, секреты подключений и внутренние таблицы миграций
отсутствуют.

Анкеты можно и смотреть, и изменять. Вкладка «Анкеты» показывает все анкеты с поиском по имени и
идентификатору. Из неё или из списка пользователей открывается редактор: та же форма, что у
пользователя, с теми же правилами проверки. Для учётной записи без анкеты редактор создаёт анкету, но
только если аккаунт существует в Keycloak. Удаление требует подтверждения в два шага и удаляет только
анкету: учётная запись, контакт и запросы на контакт остаются. Анкета исчезает из выдачи в пределах
интервала синхронизации. Каждое изменение записывается в журнал сервиса Profile: действие, идентификатор
администратора и идентификатор пользователя. Значения анкеты в журнал не попадают.

Сам администратор может удалить свою анкету, а учётные записи в панели не создаются и не удаляются:
это по-прежнему делается в консоли Keycloak.

Маршруты API через edge:

- `GET /api/profile/v1/admin/users` — пользователи; параметры `search`, `limit`, `cursor`; признак `has_profile`.
- `GET /api/profile/v1/admin/profiles` — все анкеты; параметры `search`, `limit`, `cursor`.
- `GET|PUT|DELETE /api/profile/v1/admin/users/{user_id}/profile` — анкета пользователя: просмотр,
  создание или замена (`PUT`), удаление (`DELETE`, ответ `204`).
- `GET /api/{profile|matching|interaction}/v1/admin/database` — сводка базы и список таблиц.
- `GET /api/{profile|matching|interaction}/v1/admin/tables/{table}` — строки; параметры `limit`, `cursor`.

Разрешение `DELETE` в CORS добавлено в конфигурацию edge: без него браузер блокирует удаление до
отправки запроса (`deploy/compose/edge/default.conf.template`).

Без входа API отвечает `401`, обычному пользователю — `403`. При недоступном Keycloak или выключенном
серверном клиенте вкладка пользователей показывает ошибку; просмотр собственных баз сервисов остаётся
доступен. Отсутствие ответа сервиса не означает, что его база пуста.

## Серверный доступ к пользователям

Profile использует отдельный confidential client `profile-admin-reader` с service account. Ему выдана
только client-роль `realm-management:view-users`, без `manage-users` и `realm-admin`. Стандартный вход,
implicit flow и password grant у этого клиента отключены. Секрет доступен только серверу Profile.

| Переменная                    | Локальная среда            | Production                       |
| ----------------------------- | -------------------------- | -------------------------------- |
| `KEYCLOAK_ADMIN_BASE_URL`      | `http://keycloak:8080`     | `http://keycloak:8080/id`         |
| `KEYCLOAK_ADMIN_REALM`         | `sozhiteli`               | `sozhiteli`                      |
| `KEYCLOAK_ADMIN_CLIENT_ID`     | `profile-admin-reader`    | `profile-admin-reader`           |
| `KEYCLOAK_ADMIN_CLIENT_SECRET` | генерируется setup-скриптом | задаётся владельцем развёртывания |

Не передавайте секрет в `NEXT_PUBLIC_*`, клиентские сборки или браузер. Bootstrap-пароль администратора
Keycloak нужен только локальному setup-скрипту и не передаётся в Profile. Если reader secret пустой,
Profile запускается, а получение списка пользователей остаётся недоступным.

## Production и существующие realm

Тестовый пользователь не включён в production realm. Роль администратора назначает владелец
развёртывания вручную через консоль Keycloak, доступную по SSH-туннелю согласно основной инструкции
проекта:

1. В realm `sozhiteli` создайте realm-роль `sozhiteli-admin`, если её ещё нет. Не добавляйте её в
   default roles, группы всех пользователей или роли публичных клиентов.
2. Откройте нужного пользователя: **Users → пользователь → Role mapping → Assign role → Filter by realm
   roles → sozhiteli-admin**. Для отзыва удалите это назначение. Для срочного отзыва завершите сессии
   пользователя; уже выпущенные JWT перестанут действовать по истечении срока access token.
3. Для получения пользователей создайте confidential OpenID Connect client `profile-admin-reader`.
   Включите **Client authentication** и **Service accounts roles**; отключите **Standard flow**,
   **Implicit flow**, **Direct access grants**. В **Service account roles** назначьте только client-роль
   `realm-management:view-users`.
4. Сохраните секрет клиента в закрытом `deploy/production/.env` как `KEYCLOAK_ADMIN_CLIENT_SECRET` и
   пересоздайте контейнер Profile. Секрет клиента и значение переменной должны совпадать. При свежем
   импорте realm этот секрет передаётся в Keycloak автоматически. `scripts/init-secrets.sh` его не
   генерирует; для существующего realm импорт при перезапуске не обновляет настройки.
5. У публичного `sozhiteli-web` добавьте mapper **User Realm Role** с claim `realm_access.roles`,
   `Multivalued = On`, JSON type `String`, `Add to access token = On`, `Add to ID token = Off`,
   `Add to userinfo = Off`, если эквивалентного mapper ещё нет. Роль должна быть разрешена scope клиента;
   не добавляйте её к ролям по умолчанию для достижения этого.

Файлы realm в этом проекте уже содержат роль, mapper и service account. Первый импорт создаёт их для
новой базы. Для существующего production realm внесите перечисленные настройки вручную, не удаляя
базу или Docker volumes. Не запускайте локальный setup-скрипт против production.

## Архитектурное решение: доступ админки к данным

UI читает каждый сервис через его публичный API и единый edge. Каждый сервис использует собственную
runtime-роль PostgreSQL и читает только свою базу; дополнительных прав на чужие базы нет. Админка не
добавляет общий SQL-сервис, межбазовые соединения или прямой браузерный доступ к PostgreSQL.

Для списка всех зарегистрированных аккаунтов введена явная, необязательная зависимость Profile от
Keycloak Admin REST API. Она действует только на административный маршрут пользователей. Keycloak
остаётся источником учётных записей, Profile — источником анкет; создание локальной копии каталога
пользователей потребовало бы отдельной синхронизации без пользы для первого варианта панели.
Обычные сценарии Profile и чтение баз не зависят от доступности этого административного клиента.

Панель показывает персональные данные, необходимые владельцу проекта для просмотра пользователей и
анкет, и позволяет их менять и удалять. Доступ следует давать только выбранным сотрудникам. Выдача ролей,
сброс паролей и управление учётными записями остаются в консоли Keycloak.

Изменение и удаление анкет на сервисе Profile проверяют роль `sozhiteli-admin` перед любым действием;
скрытая кнопка в интерфейсе эту проверку не заменяет.

## Проверки реализации

Проверено локально 20 октября 2026 года:

- OpenAPI-контракты валидны; Go-интерфейсы, sqlc-запросы и TypeScript-клиенты получены штатной генерацией.
- Линтеры, TypeScript, форматирование и `go mod tidy -diff` прошли; Go-линтер — 0 замечаний в четырёх модулях.
- Все unit- и интеграционные тесты Profile, Matching и Interaction прошли на отдельном временном PostgreSQL. Они проверяют доступ по роли, курсоры, таблицы и исключение значений контактов.
- `npm test`: 18 тестов клиента API и 37 исследовательских тестов прошли.
- Docker-сборки трёх сервисов и web прошли; семь контейнеров приложения запущены и healthy.
- `npm run admin:smoke`: 50 проверок прошли, 0 ошибок. Проверены 401/403/200, `no-store`, все восемь разрешённых таблиц, поиск и пагинация пользователей, курсоры городов и отклонение недопустимых таблиц/лимитов. Рабочие записи не изменяются этим тестом.
- В браузере проверены вход отдельным администратором, доступ без заполненной анкеты, обзор трёх сервисов, поиск пользователя, строки анкет и скрытие значений контактов во вкладке Interaction. Ошибок в консоли браузера не обнаружено.

Текущая версия Keycloak согласованно исключает служебные аккаунты из списка пользователей и его счётчика. Демо-анкеты, созданные без учётной записи Keycloak, видны среди строк `profile`, поэтому количество анкет и количество зарегистрированных пользователей могут различаться.
