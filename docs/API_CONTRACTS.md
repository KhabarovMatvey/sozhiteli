# API и правила контрактов

**Источник истины для API — файлы в `contracts/openapi/`.** Код сервера, типы клиента и проверка
запросов получаются из них генерацией. Этот документ описывает правила, общие для всех
контрактов; сами операции и схемы читаются в YAML.

| Контракт | Сервис | Доступ | Адрес в локальной среде |
|---|---|---|---|
| `profile.v1.yaml` | Profile | публичный | `http://localhost:8080/api/profile` |
| `matching.v1.yaml` | Matching | публичный | `http://localhost:8080/api/matching` |
| `interaction.v1.yaml` | Interaction | публичный | `http://localhost:8080/api/interaction` |
| `profile-internal.v1.yaml` | Profile | **внутренний** | `http://profile:9080` (только сеть сервисов) |

## Состояние операций

Каждая операция помечена расширением `x-implementation-status`:

- `implemented` — работает;
- `planned` — описана в контракте, сервер отвечает `501 not_implemented`.

С 2026-10-14 все операции всех контрактов — `implemented`.

Тест `TestImplementationStatusMatchesBehaviour` в каждом сервисе проверяет, что пометка
соответствует поведению. Нереализованная операция **никогда** не возвращает выдуманный успех.

## Общие правила

### Формат

- JSON, UTF-8. Имена полей — `snake_case`.
- Время — RFC 3339 в UTC (`2027-07-01T12:00:00Z`); дата — `YYYY-MM-DD`.
- Идентификаторы — UUID строкой. Деньги — целые рубли.
- Отсутствующее необязательное поле не передаётся; `null` используется только там, где схема
  объявляет `nullable: true` (сейчас это `next_cursor`).

### Аутентификация

Заголовок `Authorization: Bearer <access token>` обязателен для всех операций всех контрактов.

| API | Аудитория токена | Дополнительно |
|---|---|---|
| Публичные | `sozhiteli-api` | — |
| Внутренний | `sozhiteli-internal` | роль `internal.profile-changes.read` |

### Идентификатор запроса

Клиент может передать `X-Request-Id` (8–64 символа из `A-Z a-z 0-9 - _`); иначе его создаёт
сервис. Значение возвращается в заголовке ответа и в поле `request_id` ошибки. Клиентский пакет
подставляет его сам.

### Коды ответов

| Код | Когда | `code` в теле |
|---|---|---|
| `200` | Успешное чтение или изменение | — |
| `201` | Создан ресурс (`createContactRequest`) | — |
| `400` | Запрос не соответствует схеме: тип, формат, длина, диапазон, обязательное поле, неизвестное значение перечисления, некорректный курсор | `invalid_request` |
| `401` | Нет токена либо он недействителен | `unauthorized` |
| `403` | Токен действителен, прав недостаточно (только внутренний API) | `forbidden` |
| `404` | Ресурс не найден | код ресурса, например `profile_not_found` |
| `409` | Операция противоречит текущему состоянию | код причины, например `request_exists` |
| `422` | Схема соблюдена, нарушено бизнес-правило | `validation_failed` + `errors[]` |
| `429` | Превышен лимит | `rate_limited`, заголовок `Retry-After` |
| `500` | Непредвиденная ошибка; подробностей в ответе нет | `internal_error` |
| `501` | Операция описана, но не реализована | `not_implemented` |
| `503` | Перегрузка или недоступность, заголовок `Retry-After` | `service_unavailable` |
| `504` | Запрос не уложился в серверный таймаут | `request_timeout` |

Граница между `400` и `422`: **`400` выдаёт автоматическая проверка по схеме** (до обработчика),
**`422` — код обработчика**. Правило, выразимое в OpenAPI (`maxLength`, `enum`, `minimum`),
записывается в OpenAPI и не дублируется в коде.

Чтобы не раскрывать существование чужих ресурсов, операция над чужим запросом на контакт
отвечает `404`, а не `403`.

### Формат ошибки

Все ошибки всех сервисов и edge-прокси — `application/problem+json` (RFC 9457):

```json
{
  "type": "urn:sozhiteli:problem:validation_failed",
  "title": "Unprocessable Entity",
  "status": 422,
  "code": "validation_failed",
  "detail": "request violates validation rules",
  "request_id": "9f1c2a7e4b0d4c61a3e58f2b7d6c9e10",
  "errors": [
    { "field": "budget_max_rub", "code": "less_than_min", "message": "budget_max_rub must not be less than budget_min_rub" }
  ]
}
```

- Клиент ветвится **по `code`**. `title` и `detail` — для разработчика, их текст может меняться.
- `errors[]` присутствует только у `validation_failed`.
- Текст внутренних ошибок (SQL, сеть) в ответ не попадает никогда.

Схема `Problem` повторена в каждом контракте намеренно: контракт сервиса самодостаточен и не
зависит от общих файлов.

### Пагинация

Только курсорная.

- Запрос: `limit` (у каждой операции свои границы и значение по умолчанию) и `cursor`.
- Ответ: `items` и `next_cursor`. `next_cursor: null` — страниц больше нет.
- Курсор **непрозрачен**: клиент не разбирает и не составляет его, только возвращает как есть.
- Курсор действителен для той же операции с теми же параметрами фильтра.
- Общего количества элементов в ответах нет: его подсчёт дорог и для сценариев не нужен.
- Порядок сортировки зафиксирован в описании операции и клиентом не настраивается.

Отличие внутренней ленты: `next_cursor` там всегда строка, а конец ленты — это пустой `items`.

### Версионирование

Версия — в пути (`/v1/…`) и в имени файла контракта.

**Совместимые изменения** (в рамках `v1`):

- новая операция; новое необязательное поле запроса; новое поле ответа;
- новый код ошибки у операции, для которой уже объявлен ответ с этим HTTP-статусом;
- новая версия анкеты привычек (коды вопросов — данные, а не схема).

**Несовместимые изменения** (только через `v2`, которая работает параллельно с `v1`):

- удаление или переименование операции, поля, значения перечисления;
- изменение типа, формата или смысла поля; новое обязательное поле запроса;
- ужесточение ограничений; изменение порядка сортировки или смысла курсора;
- **добавление значения в перечисление ответа** — клиент мог не предусмотреть его.

Клиенты обязаны игнорировать неизвестные поля ответа.

### Публичные и внутренние API

| | Публичный | Внутренний |
|---|---|---|
| Префикс пути | `/v1/…` | `/internal/v1/…` |
| Порт сервиса | 8080 | 9080 |
| Маршрут через edge | да | **нет** |
| Кто вызывает | web, mobile | другие сервисы |
| TypeScript-клиент | генерируется | не генерируется |
| Согласование изменений | с клиентскими приложениями | с каждым сервисом-потребителем |

### Модели БД не раскрываются

Типы запросов и ответов генерируются из OpenAPI (`internal/api/api.gen.go`), типы строк БД — из
SQL (`internal/store`). Это **разные типы**; обработчик явно преобразует одно в другое. Возвращать
из обработчика тип пакета `store` нельзя: тогда изменение схемы БД молча меняло бы API.

## Контракт между Profile и Matching

`profile-internal.v1.yaml`, операция `listProfileChanges`. Механизм — ADR-0004.

Обязательства **Profile**:

1. Записи идут в порядке возрастания `(version, user_id)`.
2. Запись отдаётся, только когда все транзакции с меньшей версией завершены: пропусков нет.
3. `deleted: true` — без `profile`; иначе `profile` присутствует и полон.
4. Состав `ProfileSnapshot` меняется только совместимо, по согласованию с потребителем.

Обязательства **Matching**:

1. Применять запись идемпотентно и не заменять более новую версию более старой.
2. Сдвигать курсор в той же транзакции, что и применение страницы.
3. Не полагаться на то, что увидит каждое промежуточное состояние: лента отдаёт текущее.
4. При ошибке не сдвигать курсор и повторять с растущей паузой.

Обе стороны покрыты тестами: `feed_integration_test.go` (Profile) и
`syncer_integration_test.go` (Matching). Клиент Matching генерируется из того же файла
контракта, что и сервер Profile, поэтому разойтись по типам они не могут.

## Как изменить контракт

Изменение контракта — **согласуемое** действие (`CONTRIBUTING.md`): задача должна прямо его разрешать.

1. Изменить YAML в `contracts/openapi/`.
2. `npm run contracts:lint`.
3. `npm run gen` — обновятся Go-интерфейсы и TypeScript-типы.
4. Довести сервис до компиляции: новая операция появится как метод интерфейса
   `StrictServerInterface`; до реализации он возвращает `problem.NotImplemented()`.
5. Обновить таблицу «Состояние операций» выше.
6. Закоммитить контракт и сгенерированный код **одним коммитом**. CI (`gen:check`) падает, если
   они расходятся.

Две задачи не должны одновременно менять один и тот же файл контракта (`BACKLOG.md`).

## Как пользоваться контрактом на клиенте

```ts
const api = useApi(); // apps/web/src/lib/api.ts, apps/mobile/src/lib/api.ts

const { data, error } = await api.profile.GET('/v1/questionnaire');
if (error) {
  // error: Problem; ветвление по error.code
} else {
  // data типизирован по схеме Questionnaire
}
```

Прямой `fetch` в приложениях запрещён правилом линтера. Нужной операции нет в клиенте — значит,
её нет в контракте; придумывать адрес нельзя.
