# Backlog

Упорядоченный список задач после Architecture Foundation v1. Каждая задача рассчитана на одного
исполнителя и не требует знания остального проекта сверх перечисленных документов.
Правила работы и шаблон постановки задачи — `CONTRIBUTING.md`.

## Profile

Сервис: `backend/services/profile`. Контракт: `contracts/openapi/profile.v1.yaml`.
Читать: `SERVICE_BOUNDARIES.md` (Profile), `DATA_OWNERSHIP.md`, ADR-0011.

### P-01. Справочник городов

> **Выполнена 2026-10-14.** Решение Q-1 — все города России. Миграция `00002_cities.sql`
> содержит 1117 городов из справочника HFLabs (CC BY-SA 4.0, данные 2021 года) и добавляет
> городу поле `region`: у городов-тёзок разные регионы. В контракт `City` добавлено поле
> `region` (совместимое изменение). Новые города — новой миграцией с id больше 1117.

- **Цель.** `GET /v1/cities` возвращает города, в которых доступен поиск.
- **Основание.** F2; свидетельство E-COND-CITY.
- **Зависит от.** Решение Q-1 (`MVP_SCOPE.md`): список городов с идентификаторами. Без него
  задача не начинается: выбирать города самостоятельно запрещено.
- **Scope.** Миграция с наполнением таблицы `city`; запрос; обработчик `ListCities`.
- **Разрешённые файлы.** `migrations/00002_seed_cities.sql` (новый), `internal/store/queries/cities.sql`
  (новый), `internal/api/server.go`, `internal/api/*_test.go`, `cmd/profile/main.go` (передать
  `*store.Queries` в `api.NewServer`), `contracts/openapi/profile.v1.yaml` (только пометка статуса).
- **Контракты.** Операция `listCities`, схемы `CityList`, `City`.
- **Правила.**
  - Миграция: `INSERT INTO city (id, name) VALUES …` по списку из Q-1; `Down` удаляет эти строки.
  - Запрос: `SELECT id, name FROM city ORDER BY name`. Справочник мал, пагинации нет.
  - `api.Server` получает поле `queries *store.Queries`; `NewServer(queries)`.
- **Критерии приёмки.** Операция отвечает `200` со списком в алфавитном порядке; пометка
  `implemented`; существующие тесты проходят.
- **Обязательные тесты.** Интеграционный: после миграций список не пуст и отсортирован; ответ
  проходит `openapitest.AssertResponse`.
- **Запрещено.** Добавлять города, которых нет в Q-1; добавлять поля в `City`.

### P-02. Чтение своей анкеты

- **Цель.** `GET /v1/me/profile` возвращает анкету вызывающего.
- **Основание.** F2, F3: пользователь должен видеть и исправлять свою анкету.
- **Зависит от.** P-01 (только из-за общего файла `server.go`; если Q-1 не решён — выполняется
  первой, добавив `queries` в `Server` самостоятельно, как описано в P-01).
- **Разрешённые файлы.** `internal/store/queries/profile.sql` (новый), `internal/api/server.go`,
  `internal/api/convert.go` (новый: преобразование строки БД в `Profile`), тесты, пометка статуса.
- **Контракты.** `getMyProfile`, схема `Profile`.
- **Правила.**
  - Пользователь — `auth.UserID(ctx)`.
  - Запрос `GetProfile :one` по `user_id`, все столбцы, кроме `feed_version`.
  - Нет строки (`pgx.ErrNoRows`) → `problem.NotFound("profile_not_found", …)`.
  - `habits` из `jsonb` разбирается в `map[string]string`.
- **Критерии приёмки.** Без анкеты — `404 profile_not_found`; с анкетой — `200`; чужую анкету
  получить невозможно ни при каких параметрах.
- **Обязательные тесты.** Интеграционные: `404` для нового пользователя; `200` для пользователя с
  анкетой (строка вставлена в тесте SQL-запросом, как в `feed_integration_test.go`); пользователь
  B не получает анкету A. Все ответы — через `AssertResponse`.

### P-03. Сохранение анкеты

- **Цель.** `PUT /v1/me/profile` создаёт или полностью заменяет анкету.
- **Основание.** F2, F3, F8.
- **Зависит от.** P-02.
- **Разрешённые файлы.** `internal/store/queries/profile.sql`, `internal/api/server.go`,
  `internal/api/convert.go`, `internal/profilerules/` (новый пакет: чистая проверка анкеты),
  `internal/questionnaire/questionnaire.go` (только добавление метода проверки ответов), тесты,
  пометка статуса.
- **Контракты.** `putMyProfile`, схемы `ProfileInput`, `Profile`, `Problem`, `FieldError`.
- **Правила.** Проверка по схеме уже выполнена до обработчика; ниже — только бизнес-правила.
  Все нарушения собираются и возвращаются **одним** ответом `422` через `problem.Validation(…)`.

  | Поле (`field`) | Правило | `code` |
  |---|---|---|
  | `display_name`, `occupation`, `districts` | После `strings.TrimSpace` длина в границах контракта | `out_of_range` |
  | те же | Не содержит контактов: символа `@`; подстрок `http`, `www.`, `t.me`, `vk.com`, `wa.me` (без учёта регистра); 7 и более цифр подряд, если убрать пробел, `-`, `(`, `)` | `contact_not_allowed` |
  | `birth_year` | Возраст `текущий год − birth_year` не меньше 18 | `too_young` |
  | `birth_year` | Возраст не больше 100 | `out_of_range` |
  | `city_id` | Существует в `city` | `unknown_city` |
  | `budget_max_rub` | Не меньше `budget_min_rub` | `less_than_min` |
  | `move_in_to` | Не раньше `move_in_from` | `before_from` |
  | `move_in_to` | Не раньше сегодняшней даты (UTC) | `in_past` |
  | `questionnaire_version` | Равна `questionnaire.Current().Version` | `unsupported_version` |
  | `habits.<код>` | Для каждого вопроса версии есть ответ | `required` |
  | `habits.<код>` | Код вопроса существует в версии | `unknown_question` |
  | `habits.<код>` | Код варианта существует у вопроса | `unknown_option` |

  - Текущее время передаётся в функцию проверки параметром, а не берётся внутри неё.
  - Запись: `INSERT … ON CONFLICT (user_id) DO UPDATE SET …` всех полей анкеты, `RETURNING` всех
    столбцов ответа. `created_at`, `updated_at`, `feed_version` в запросе **не указываются**: их
    ставят значения по умолчанию и триггер.
  - Сохраняются значения текстовых полей после `TrimSpace`.
  - Существование города проверяется одним запросом до записи; нарушение внешнего ключа при
    гонке также преобразуется в `unknown_city`.
- **Критерии приёмки.** Первое сохранение создаёт анкету, повторное заменяет её, сохраняя
  `created_at`; каждое правило таблицы даёт `422` с указанным `code` и `field`; несколько
  нарушений приходят вместе; после сохранения запись появляется в ленте изменений.
- **Обязательные тесты.** Юнит (табличные) на `profilerules`: каждое правило, границы возраста и
  дат, варианты записи контактов. Интеграционные: создание, замена, `created_at` не меняется,
  запись видна через `GET /internal/v1/profile-changes`; контрактные для `200` и `422`.
- **Запрещено.** Частичное обновление (PATCH); новые поля анкеты; запись `feed_version` из кода;
  изменение триггеров; логирование значений полей.

## Matching

Сервис: `backend/services/matching`. Контракт: `contracts/openapi/matching.v1.yaml`.
Читать: `SERVICE_BOUNDARIES.md` (Matching), ADR-0004, ADR-0010, ADR-0011.

Данные для тестов вставляются в таблицу `candidate` SQL-запросом в самом тесте: задачи Matching
**не зависят** от готовности Profile. Обращаться к Profile из обработчиков запрещено.

### M-01. Выдача кандидатов

- **Цель.** `GET /v1/candidates` возвращает страницу кандидатов, прошедших обязательные условия.
- **Основание.** F4; E-COMPARE-UNEVEN, E-STALE.
- **Зависит от.** —
- **Разрешённые файлы.** `internal/store/queries/candidates.sql` (новый), `internal/compare/`
  (новый пакет: чистое сравнение анкет), `internal/api/server.go`, `internal/api/convert.go`
  (новый), `internal/api/cursor.go` (новый), `cmd/matching/main.go` (передать `*store.Queries` в
  `api.NewServer`), тесты, пометка статуса.
- **Контракты.** `listCandidates`, схемы `CandidatePage`, `CandidateCard`, `Compatibility`.
- **Правила.**
  - Зритель — `auth.UserID(ctx)`. Его строка читается из `candidate`. Строки нет →
    `problem.Conflict("profile_not_ready", …)` с `RetryAfter = 5 * time.Second`.
  - Запрос выдачи (один запрос, без запросов в цикле), `v` — значения зрителя:

    ```sql
    WHERE c.search_status = 'searching'
      AND c.city_id = v.city_id
      AND c.user_id <> v.user_id
      AND c.budget_min_rub <= v.budget_max_rub AND c.budget_max_rub >= v.budget_min_rub
      AND c.move_in_from <= v.move_in_to AND c.move_in_to >= v.move_in_from
      AND (v.roommate_gender = 'any' OR c.gender = v.gender)
      AND (c.roommate_gender = 'any' OR c.gender = v.gender)
      AND (c.profile_updated_at, c.user_id) < (курсор)      -- если курсор передан
    ORDER BY c.profile_updated_at DESC, c.user_id DESC
    LIMIT limit + 1
    ```

  - Статус поиска самого зрителя на выдачу не влияет.
  - Запрошена `limit + 1` строка: если пришла лишняя — она отбрасывается, а `next_cursor`
    строится по последней строке страницы; иначе `next_cursor = null`.
  - Курсор — base64url от `"<profile_updated_at в RFC3339Nano>|<user_id>"`. Некорректный курсор →
    `problem.InvalidRequest("cursor is not valid")`.
  - `age = текущий год − birth_year`.
  - `compatibility` (пакет `compare`): `compared_count` — число кодов вопросов, присутствующих в
    ответах **обоих**; `matched_count` — сколько из них имеют одинаковый код варианта.
- **Критерии приёмки.** Каждое условие фильтра исключает неподходящего кандидата; сам зритель и
  анкеты на паузе в выдачу не попадают; страницы не пересекаются и не теряют строк; порядок — по
  убыванию времени обновления.
- **Обязательные тесты.** Юнит на `compare` и на курсор. Интеграционные: по одному кандидату на
  каждое условие фильтра (подходит / не подходит); пагинация на 5 кандидатах при `limit=2`;
  `409 profile_not_ready` без строки зрителя; все ответы через `AssertResponse`.
- **Запрещено.** Сортировка по числу совпадений, веса, параметры фильтра от клиента; вызов
  Profile; `OFFSET`.

### M-02. Карточка кандидата со сравнением

- **Цель.** `GET /v1/candidates/{user_id}` возвращает карточку, сравнение условий и ответов и
  фиксирует факт просмотра.
- **Основание.** F5 (ядро гипотезы), F9.
- **Зависит от.** M-01.
- **Разрешённые файлы.** `internal/store/queries/candidates.sql`, `internal/compare/`,
  `internal/api/server.go`, `internal/api/convert.go`, тесты, пометка статуса.
- **Контракты.** `getCandidate`, схемы `CandidateDetail`, `ConditionsComparison`, `HabitComparison`.
- **Правила.**
  - Зритель — как в M-01, включая `409 profile_not_ready`.
  - Кандидат читается по `user_id` **при любом** `search_status`. Нет строки либо запрошен сам
    зритель → `problem.NotFound("candidate_not_found", …)`.
  - `conditions`: `same_city` — равенство `city_id`; `budget_overlap` и `move_in_overlap` — те же
    неравенства, что в фильтре M-01; `roommate_gender_ok` — оба условия по полу из M-01.
  - `habits`: по одному элементу на каждый код вопроса, встречающийся в ответах хотя бы одной
    стороны, в алфавитном порядке кодов. Оба ответили одинаково → `match`; оба по-разному →
    `difference`; ответил один → `not_comparable`, отсутствующее поле не передаётся.
  - `my_option` — ответ зрителя, `their_option` — ответ кандидата.
  - После успешного чтения — `INSERT INTO candidate_view (viewer_id, candidate_id, matched_count,
    compared_count)`. Ошибка записи — ошибка операции (`500`): факт просмотра нужен эксперименту.
- **Критерии приёмки.** Сравнение корректно для совпадающих, различающихся и отсутствующих
  ответов; каждый успешный вызов добавляет ровно одну строку в `candidate_view`; неуспешный — ни одной.
- **Обязательные тесты.** Юнит на `compare` (три вида результата, порядок, анкеты разных версий).
  Интеграционные: `200` и строка в `candidate_view` с верными счётчиками; `404` для
  несуществующего и для самого себя без строки в `candidate_view`; кандидат на паузе доступен.
- **Запрещено.** Возвращать контакт или любые данные, которых нет в схеме; подписи вопросов
  (их отдаёт Profile); вызов других сервисов.

### M-03. Карточки по списку идентификаторов

- **Цель.** `POST /v1/candidates/lookup` возвращает карточки для экранов запросов на контакт.
- **Основание.** Технический шаг F7: без него экран запросов делал бы запрос на каждую строку.
- **Зависит от.** M-02.
- **Разрешённые файлы.** как в M-02.
- **Контракты.** `lookupCandidates`, схемы `CandidateLookupRequest`, `CandidateList`.
- **Правила.** Зритель — как в M-01. Один запрос `WHERE user_id = ANY($1)`. Идентификатор самого
  зрителя и отсутствующие идентификаторы в ответ не попадают. Порядок — как в запросе. Фильтр
  обязательных условий **не применяется**. `compatibility` считается как в M-01.
- **Критерии приёмки.** Возвращаются только существующие карточки, в порядке запроса; 50
  идентификаторов обслуживаются одним SQL-запросом.
- **Обязательные тесты.** Интеграционные: смесь существующих, отсутствующих и собственного
  идентификатора; порядок; `409 profile_not_ready`.
- **Запрещено.** Запись в `candidate_view` (это не просмотр карточки со сравнением).

## Interaction

Сервис: `backend/services/interaction`. Контракт: `contracts/openapi/interaction.v1.yaml`.
**Обязательно читать:** `SECURITY.md` (разделы «Правило раскрытия контакта» и «Правила
логирования»), ADR-0005.

Для всех задач цепочки: значения контактов не логируются; чужой контакт возвращается только по
правилу раскрытия.

### I-01. Собственный контакт

- **Цель.** `GET` и `PUT /v1/me/contact`.
- **Основание.** F6; E-CONTACT-CHANNEL.
- **Зависит от.** —
- **Разрешённые файлы.** `internal/store/queries/contact.sql` (новый), `internal/contactrules/`
  (новый пакет), `internal/api/server.go`, `cmd/interaction/main.go` (передать `*store.Queries` и
  конфигурацию в `api.NewServer`), тесты, пометки статуса обеих операций.
- **Контракты.** `getMyContact`, `putMyContact`, схема `Contact`.
- **Правила.**
  - `GET`: нет строки → `problem.NotFound("contact_not_found", …)`.
  - `PUT`: `INSERT … ON CONFLICT (user_id) DO UPDATE SET kind, value, updated_at = now()`.
  - Формат `value` (нарушение → `422`, `field: "value"`, `code: "invalid_format"`):
    `telegram` — `^[A-Za-z][A-Za-z0-9_]{4,31}$`; `vk` — `^[A-Za-z0-9_.]{2,32}$`.
    Ведущий `@` и ссылки не исправляются автоматически, а отклоняются.
- **Критерии приёмки.** Контакт создаётся и заменяется; чужой контакт получить невозможно.
- **Обязательные тесты.** Юнит (табличные) на формат обоих видов. Интеграционные: `404` → `PUT` →
  `GET`; замена; пользователь B не видит контакт A.
- **Запрещено.** Другие виды контакта; несколько контактов; проверка существования аккаунта во
  внешних сервисах.

### I-02. Создание запроса на контакт

- **Цель.** `POST /v1/contact-requests`.
- **Основание.** F7 — конечная точка эксперимента.
- **Зависит от.** I-01.
- **Разрешённые файлы.** `internal/store/queries/requests.sql` (новый), `internal/api/server.go`,
  `internal/api/convert.go` (новый), тесты, пометка статуса.
- **Контракты.** `createContactRequest`, схемы `ContactRequestCreate`, `ContactRequest`.
- **Правила.** Все шаги — в **одной транзакции**, в этом порядке:
  1. `recipient_id` равен отправителю → `problem.Validation` с `field: "recipient_id"`,
     `code: "self_request"`.
  2. Блокировка пары, чтобы два встречных запроса не создались одновременно:
     `SELECT pg_advisory_xact_lock(hashtextextended(least($1::text, $2::text) || ':' || greatest($1::text, $2::text), 0))`.
  3. У отправителя нет контакта → `problem.Conflict("contact_required", …)`.
  4. Есть запрос от отправителя этому получателю (любой статус) → `Conflict("request_exists", …)`.
  5. Есть запрос от получателя отправителю (любой статус) → `Conflict("reverse_request_exists", …)`.
  6. Число запросов отправителя с `created_at > now() - interval '24 hours'` не меньше
     `ContactRequestDailyLimit` → `problem.TooManyRequests(time.Hour)`.
  7. `INSERT … RETURNING`. Нарушение уникальности (гонка) → `request_exists`.
  - Ответ `201`: `direction: "outgoing"`, `counterpart_id` — получатель, `status: "pending"`,
    **без** `counterpart_contact`.
  - Существование анкеты получателя не проверяется (ADR-0005).
- **Критерии приёмки.** Каждое правило даёт указанный код; успешный запрос создаёт одну строку;
  контакт получателя не возвращается.
- **Обязательные тесты.** Интеграционные на каждый из шагов 1, 3–6 и на успех; лимит проверяется
  при `ContactRequestDailyLimit = 2`; тест гонки: два одновременных встречных запроса — создаётся
  ровно один; ответ успеха не содержит `counterpart_contact`.
- **Запрещено.** Вызов Profile или Matching; авто-принятие встречного запроса; уведомления.

### I-03. Списки запросов

- **Цель.** `GET /v1/contact-requests`.
- **Основание.** F7.
- **Зависит от.** I-02.
- **Разрешённые файлы.** как в I-02, плюс `internal/api/cursor.go` (новый).
- **Контракты.** `listContactRequests`, схема `ContactRequestPage`.
- **Правила.**
  - `direction=incoming` — `recipient_id` равен вызывающему; `outgoing` — `sender_id`.
  - `counterpart_id`, если передан, — дополнительное равенство по второму участнику.
  - Порядок `created_at DESC, id DESC`; keyset-курсор и `limit + 1` — как в M-01
    (`"<created_at RFC3339Nano>|<id>"`).
  - **Контакт собеседника — в том же запросе**: `LEFT JOIN contact ON contact.user_id =
    <второй участник> AND contact_request.status = 'accepted'`. Никаких запросов в цикле.
  - `counterpart_contact` присутствует только у `accepted`; у `pending` и `declined` поля нет.
  - `responded_at` присутствует только когда статус не `pending`.
- **Критерии приёмки.** Пользователь видит только запросы со своим участием; контакт виден только
  в принятых; страницы не пересекаются.
- **Обязательные тесты.** Интеграционные: оба направления; фильтр `counterpart_id`; пагинация;
  **контакт отсутствует у `pending` и `declined` и присутствует у `accepted` для обеих сторон**;
  третий пользователь не видит чужих запросов.

### I-04. Принятие и отклонение запроса

- **Цель.** `POST /v1/contact-requests/{request_id}/accept` и `/decline`.
- **Основание.** F7: согласие получателя на раскрытие контакта.
- **Зависит от.** I-03.
- **Разрешённые файлы.** как в I-02.
- **Контракты.** `acceptContactRequest`, `declineContactRequest`.
- **Правила.** В одной транзакции:
  1. Только для `accept`: у вызывающего нет контакта → `Conflict("contact_required", …)`.
  2. `UPDATE contact_request SET status = …, responded_at = now() WHERE id = $1 AND
     recipient_id = $2 AND status = 'pending' RETURNING …`.
  3. Строка не обновлена: если запрос с таким `id` и `recipient_id` существует →
     `Conflict("already_responded", …)`; иначе → `NotFound("contact_request_not_found", …)`.
     Отправитель запроса и посторонний получают одинаковый `404`.
  - Ответ: `direction: "incoming"`. Для `accept` — с `counterpart_contact` отправителя, прочитанным
    из `contact` в той же транзакции. Для `decline` — без контакта.
- **Критерии приёмки.** Ответить может только получатель и только один раз; после принятия обе
  стороны видят контакты друг друга через `listContactRequests`; после отклонения — никто.
- **Обязательные тесты.** Интеграционные: принятие и отклонение; повторный ответ → `409`;
  отправитель и посторонний → `404`; принятие без контакта → `409 contact_required`; сквозной
  сценарий правила раскрытия: создание → контактов нет → принятие → контакты у обоих.
- **Запрещено.** Отмена запроса; изменение ответа; копирование контакта в `contact_request`.
