# Правила для разработчиков, продолжающих проект

Этот документ читается **первым и целиком** перед любой работой в репозитории.

Архитектура проекта уже спроектирована. Твоя работа — реализовывать заранее описанные задачи
внутри заданных границ. Системные решения ты не принимаешь: если задача без них не выполняется,
ты останавливаешься и сообщаешь об этом.

## 2. Что можно делать самостоятельно

- Реализовывать операции, уже описанные в контракте (`x-implementation-status: planned`).
- Писать код внутри сервиса или приложения, названного в задаче, в существующей структуре каталогов.
- Добавлять SQL-запросы в `internal/store/queries/` и миграции в `migrations/` **своего** сервиса.
- Создавать экраны и компоненты по существующим контрактам.
- Писать и дополнять тесты.
- Исправлять ошибки в коде, который относится к задаче.
- Обновлять документацию своего компонента: таблицу операций в `API_CONTRACTS.md`, переменные
  окружения в `ENGINEERING_RULES.md`, состояние задачи в `BACKLOG.md`.
- Добавлять в пакет предметной области сервиса (`internal/<domain>/`) чистые функции.

## 3. Что запрещено без отдельного архитектурного согласования

Согласование — это явное разрешение в тексте задачи или новый ADR, принятый владельцем
архитектуры. Собственное убеждение, что «так будет лучше», согласованием не является.

**Архитектура**

- Изменять границы и ответственность сервисов; переносить функцию в другой сервис.
- Создавать новые сервисы, новые исполняемые файлы, новые фоновые процессы.
- Добавлять вызов одного сервиса из другого; вызывать другой сервис при обработке запроса пользователя.
- Объединять сервисы, заменять архитектуру монолитом или «временно» общим кодом.
- Добавлять инфраструктуру: брокеры, кэши, поисковые движки, очереди, оркестраторы, сторонние сервисы.
- Менять технологический стек и версии из `ENGINEERING_RULES.md`.

**Данные**

- Обращаться к базе данных другого сервиса любым способом.
- Создавать таблицы с данными, которыми владеет другой сервис (кроме проекции `candidate`).
- Хранить контакты где-либо, кроме `interaction_db.contact`.
- Добавлять в `backend/platform` типы и правила предметной области.
- Редактировать уже существующие файлы миграций.

**Контракты**

- Менять файлы в `contracts/openapi/`, если задача прямо этого не разрешает.
- Придумывать адреса, поля и коды ошибок, которых нет в контракте.
- Возвращать успех из нереализованной операции; возвращать выдуманные данные.
- Редактировать сгенерированные файлы (`*.gen.go`, `internal/store/*.go`,
  `packages/api-client/src/generated/`).

**Безопасность**

- Менять способ аутентификации, проверку токенов, настройки realm, CORS, сети Compose.
- Брать идентификатор пользователя из запроса вместо `auth.UserID(ctx)`.
- Возвращать чужой контакт вне правила из `SECURITY.md`.
- Логировать тела запросов, токены, контакты, значения полей анкеты.
- Писать собственную криптографию; отключать проверки в тестах и в коде.

**Продукт**

- Добавлять функции, поля, экраны, вопросы анкеты, которых нет в задаче. Каждая пользовательская
  функция в этом проекте требует исследовательского обоснования (`FEATURE_JUSTIFICATION.md`), и
  его нельзя придумать.
- Ссылаться на результаты исследования, которых нет в `RESEARCH_EVIDENCE.md`: выдумывать цитаты,
  цифры и выводы интервью.

**Процесс**

- Удалять, пропускать или ослаблять тесты и проверки CI.
- Менять код, не относящийся к задаче: попутный рефакторинг, переименования, переформатирование.
- Объединять несколько задач в одно изменение.

## 4. Когда остановиться и спросить

Остановись, ничего не меняя в спорном месте, и опиши проблему, если:

- задача не выполняется без действия из раздела 3;
- контракт и текст задачи противоречат друг другу;
- в контракте не хватает поля, кода ошибки или операции;
- существующий тест нужно изменить, чтобы твой код прошёл;
- непонятно, какому сервису принадлежит функция или данные;
- требование задачи нарушает правило из `SECURITY.md`;
- для задачи нужно продуктовое решение (текст, порог, правило), которого нет в задаче.

Формат сообщения: **что мешает** · **какие варианты ты видишь** · **что из них потребует
изменить в архитектуре или контракте**. Не выбирай вариант сам и не реализуй «на всякий случай»
оба.

## 5. Порядок выполнения задачи

1. Прочитай задачу и перечисленные в ней документы. Убедись, что зависимости задачи выполнены.
2. Открой контракт операции: запрос, ответы, коды ошибок.
3. Открой эталонный код из раздела 1.
4. Если нужна база данных: напиши SQL в `internal/store/queries/`, при необходимости миграцию;
   выполни `npm run gen`.
5. Реализуй логику. Чистые правила — в `internal/<domain>/` с юнит-тестами; обработчик — в
   `internal/api/server.go`.
6. Замени `problem.NotImplemented()` реализацией. В контракте поставь
   `x-implementation-status: implemented` (это единственное разрешённое без согласования
   изменение контракта) и выполни `npm run gen`.
7. Напиши тесты из раздела «Обязательные тесты» задачи.
8. Выполни проверки:
   - backend: `npm run backend:fmt`, `backend:vet`, `backend:lint`, `backend:test:integration`;
   - клиенты: `npm run lint`, `typecheck`, `test`, `format:check`, сборка приложения;
   - при изменении контракта или SQL: `npm run contracts:lint`, `npm run gen:check` после коммита.
9. Обнови документацию: строку операции в `API_CONTRACTS.md`, состояние задачи в `BACKLOG.md`.
10. Составь отчёт по форме из раздела 7.

## 6. Формат задачи

Каждая задача в `BACKLOG.md` содержит одни и те же поля. Задача без какого-либо из них к
выполнению не принимается — верни её постановщику.

| Поле | Содержание |
|---|---|
| **Цель** | Что должно начать работать |
| **Основание** | Код функции из `FEATURE_JUSTIFICATION.md` либо техническое основание |
| **Зависит от** | Задачи, которые должны быть завершены раньше |
| **Scope** | Что именно входит; при необходимости — что не входит |
| **Разрешённые файлы** | Каталоги и файлы, которые можно менять. Всё остальное менять нельзя |
| **Контракты** | Операции и схемы, которые реализуются |
| **Правила** | Точные бизнес-правила, коды ошибок, SQL-условия. Додумывать не нужно |
| **Критерии приёмки** | Проверяемые утверждения |
| **Обязательные тесты** | Какие тесты должны появиться |
| **Запрещено** | Что нельзя трогать именно в этой задаче, сверх раздела 3 |

## 7. Отчёт о выполнении

```
Задача: <идентификатор и название>

Сделано:
- <что реализовано, по пунктам критериев приёмки>

Изменённые файлы:
- <путь> — <что изменено>

Проверки (выполнены запуском):
- npm run backend:test:integration — пройдено / не пройдено: <вывод>
- <остальные команды>

Не проверено:
- <что не удалось проверить и почему>

Отклонения от задачи и открытые вопросы:
- <или «нет»>
```

Правила отчёта: «проверено» пишется только о том, что действительно запущено и прошло. Упавшая
проверка приводится с выводом. Если что-то из задачи не сделано — это написано прямо.

## 9. Параллельная работа

- Задачи **разных сервисов и приложений** независимы и могут выполняться одновременно:
  цепочки `P-…`, `M-…`, `I-…`, `W-…` не пересекаются по файлам.
- Задачи **одного сервиса** выполняются по порядку: они меняют одни и те же `server.go` и
  `queries/`.
- **Один файл контракта одновременно меняет не более одной задачи.** Смена пометки
  `x-implementation-status` затрагивает только свою операцию и конфликтов по смыслу не создаёт,
  но слияние выполняется последовательно.
- Клиентская задача может начинаться до серверной: контракт уже есть. Сквозная проверка экрана
  возможна после завершения серверной задачи.
- `backend/platform`, `contracts/`, `deploy/`, `tools/`, `.github/` — общие области. Задачи их
  не меняют, если это не указано прямо.
