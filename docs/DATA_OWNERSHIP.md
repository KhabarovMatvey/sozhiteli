# Владение данными

## Принцип

У каждой единицы данных **один владелец** — сервис, который один имеет право её изменять.
Остальные получают данные только через контракт владельца и могут хранить **копию для чтения**.

Изоляция обеспечена физически, а не договорённостью (ADR-0003):

| Сервис | База | Роль миграций (владелец схемы) | Рабочая роль (только строки) |
|---|---|---|---|
| Profile | `profile_db` | `profile_migrator` | `profile_app` |
| Matching | `matching_db` | `matching_migrator` | `matching_app` |
| Interaction | `interaction_db` | `interaction_migrator` | `interaction_app` |
| Keycloak | `keycloak_db` | `keycloak_app` | `keycloak_app` |

- Базы разные, а запросов между базами в PostgreSQL нет: `JOIN` с чужой таблицей написать нельзя.
- Рабочая роль сервиса не может подключиться к чужой базе и не может менять схему своей.
- Сервис получает строку подключения только к своей базе.

Проверяется автоматически: `npm run infra:smoke`, блок «Изоляция данных между сервисами».
Роли и базы создаёт `deploy/compose/postgres/init/10-databases.sh`.

## Что кому принадлежит

### Profile — `profile_db`

Схема: `backend/services/profile/migrations/`.

| Таблица | Содержимое | Персональные данные |
|---|---|---|
| `profile` | Анкета: имя, год рождения, пол, род занятий, город, районы, бюджет, сроки, предпочтение по полу соседа, ответы о привычках, статус поиска | да |
| `profile_deletion` | Отметки об удалённых анкетах для ленты изменений: идентификатор и версия | нет (только идентификатор) |
| `city` | Справочник городов России: название и регион; идентификаторы неизменны (миграция `00002_cities.sql`, источник — HFLabs, CC BY-SA 4.0) | нет |

Определение анкеты привычек (вопросы, варианты, версии) — тоже данные Profile, но хранятся в
коде: `internal/questionnaire`.

Служебные столбцы `profile.updated_at` и `profile.feed_version` выставляет триггер
`profile_touch`. **Приложение их не записывает.** Триггер `profile_record_deletion` при удалении
строки сам создаёт отметку в `profile_deletion`. Благодаря этому любое изменение анкеты попадает
в ленту, даже если автор запроса о ленте не знает.

### Matching — `matching_db`

Схема: `backend/services/matching/migrations/`.

| Таблица | Содержимое | Владелец данных |
|---|---|---|
| `candidate` | **Копия** анкет из Profile | Profile. Matching только применяет ленту; изменять строки по собственной инициативе запрещено |
| `sync_state` | Позиция чтения ленты | Matching |
| `candidate_view` | Факты просмотра карточки: кто, кого, сколько совпало, когда | Matching |

`candidate` можно полностью пересоздать: `TRUNCATE candidate; UPDATE sync_state SET feed_cursor = ''`.

### Interaction — `interaction_db`

Схема: `backend/services/interaction/migrations/`.

| Таблица | Содержимое | Персональные данные |
|---|---|---|
| `contact` | Контакт пользователя: вид (Telegram или ВК) и значение | да, **самые чувствительные в системе** |
| `contact_request` | Запрос на контакт: отправитель, получатель, статус, время | да (связь между людьми) |

### Keycloak — `keycloak_db`

Учётные записи, email, хэши паролей, сессии. Имени и фамилии нет: регистрация — только почта
и пароль (ADR-0013). Схемой управляет сам Keycloak.

## Идентификатор пользователя

Во всех сервисах пользователь — это `user_id uuid`, равный claim `sub` access-токена Keycloak.

- Это **единственное**, что связывает данные одного человека в разных сервисах.
- Внешних ключей между сервисами нет и быть не может.
- Сервис берёт `user_id` вызывающего из токена (`auth.UserID(ctx)`), а не из запроса.
- Таблицы «пользователь» нет ни в одном сервисе: учётная запись живёт в Keycloak, а факт «у
  человека есть анкета» — это строка в `profile`.

## Передача данных между сервисами

Одна передача: анкеты из Profile в Matching, по ленте изменений (ADR-0004).

| Свойство | Значение |
|---|---|
| Направление | Matching запрашивает у Profile; Profile о Matching не знает |
| Что передаётся | Текущее состояние изменившихся анкет целиком и отметки об удалении |
| Чего там нет | Контактов (их нет в Profile), email и любых данных Keycloak |
| Гарантии | Без пропусков; возможны повторы — потребитель применяет идемпотентно, сравнивая версии |
| Задержка | До `SYNC_INTERVAL` (по умолчанию 5 с) в штатном режиме |
| Согласованность | В конечном счёте (eventual): после изменения анкеты выдача некоторое время показывает прежнее состояние |

Следствие, которое должны учитывать исполнители: **сразу после сохранения анкеты Matching может
ещё не знать о ней.** Это штатное поведение, а не ошибка; клиент обрабатывает `409 profile_not_ready`.

## Данные одного человека в трёх сервисах

| Данные | Где | Кому видны |
|---|---|---|
| Email, пароль | Keycloak | Только самому пользователю на странице Keycloak |
| Анкета | Profile (оригинал), Matching (копия) | Владельцу — целиком; другим вошедшим пользователям — как карточка кандидата |
| Контакт | Interaction | Владельцу; второму участнику — только при принятом запросе |
| Факт запроса на контакт | Interaction | Только двум участникам |
| Факты просмотров | Matching | Никому из пользователей; только команде при выгрузке |

## Удаление данных пользователя

В MVP — ручная операция оператора (`MVP_SCOPE.md`, шаг 4). Порядок важен:

1. Interaction: удалить строки `contact` и `contact_request`, где пользователь — участник.
2. Profile: `DELETE FROM profile WHERE user_id = …` — триггер создаст отметку, и копия исчезнет
   из Matching в пределах интервала синхронизации.
3. Matching: удалить строки `candidate_view`, где пользователь — зритель или кандидат.
4. Keycloak: удалить учётную запись.

Команды — в `SECURITY.md`. Автоматизация — отдельная задача после эксперимента: потребуется
доставка события об удалении в Interaction, то есть второе межсервисное взаимодействие и ADR.

## Правила изменения схемы

1. Схему меняют только миграции сервиса-владельца: новый файл `NNNNN_описание.sql` в его каталоге
   `migrations/`. Применённые миграции не редактируются.
2. У каждой миграции есть `-- +goose Down`; откат проверяется интеграционным тестом.
3. Миграции выполняются отдельным шагом (`<service> migrate up`) под ролью `<service>_migrator`,
   **до** запуска новой версии сервиса.
4. Изменение должно быть совместимо с работающей предыдущей версией сервиса (expand → migrate →
   contract): сначала добавить столбец, затем начать писать, и только отдельной поздней миграцией
   удалить старый.
5. **Схема базы — не контракт.** Ни один другой сервис от неё не зависит, поэтому её можно менять
   свободно, пока не меняется API. Модели БД через API не раскрываются: типы ответов генерируются
   из OpenAPI, а не из таблиц.
6. Изменение состава ленты изменений (`ProfileSnapshot`) — это изменение контракта и требует
   согласования с потребителем (`API_CONTRACTS.md`).
