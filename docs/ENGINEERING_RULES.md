# Правила разработки

Обязательны для всех, кто меняет репозиторий. Правила, проверяемые
автоматически, помечены ✅ — их нарушение останавливает CI.

## Команды

Все команды запускаются из корня и одинаково работают в Windows, macOS, Linux и CI.

| `npm run infra:up` / `infra:down` / `infra:reset` | Локальная среда: поднять / остановить / остановить и стереть данные |
| `npm run infra:smoke` | Сквозная инфраструктурная проверка запущенной среды |

| `npm run contracts:lint` | Проверка OpenAPI |

| `npm run backend:test` | Юнит- и контрактные тесты Go |
| `npm run backend:test:integration` | То же + интеграционные тесты на временном PostgreSQL |
| `npm run lint` / `typecheck` / `test` / `format:check` | Проверки TypeScript |
| `npm run web:dev` / `web:build` | Web-приложение |
| `npm run mobile:start` | Mobile-приложение |
| `npm run web -w @sozhiteli/mobile` | Mobile-приложение в браузере (react-native-web), порт 8082 |

изменённого приложения. Изменён контракт или SQL — сначала `npm run gen`.

## Структура сервиса

Все три сервиса устроены одинаково. Новый код кладётся в существующие места; новые каталоги
верхнего уровня в сервисе не создаются.

```
cmd/<service>/main.go       сборка зависимостей и запуск; логики нет
internal/config/            чтение переменных окружения
internal/api/api.gen.go     СГЕНЕРИРОВАНО из OpenAPI — не редактировать
internal/api/router.go      подключение middleware; менять не требуется
internal/api/server.go      обработчики операций (StrictServerInterface)
internal/store/queries/     SQL-запросы — пишутся вручную
internal/store/*.go         СГЕНЕРИРОВАНО sqlc — не редактировать
internal/<domain>/          чистая логика предметной области без HTTP и SQL
migrations/NNNNN_*.sql      миграции
```

Зависимости направлены в одну сторону: `cmd → api → (domain, store)`. Пакет предметной области
не импортирует `api` и `store`. ✅ Циклы невозможны: компилятор Go их отклоняет.

## Конфигурация

Только переменные окружения, читаются один раз при старте в `internal/config`. Обращаться к
`os.Getenv` в другом месте запрещено. Отсутствие обязательной переменной — ошибка старта с
перечислением всех проблем сразу.

Общие переменные (`platform/config.Base`):

| Переменная | Назначение | По умолчанию |
|---|---|---|
| `HTTP_ADDR` | Адрес публичного API | `:8080` |
| `LOG_LEVEL` | `debug`, `info`, `warn`, `error` | `info` |
| `REQUEST_TIMEOUT` | Таймаут обработки запроса | `5s` |
| `SHUTDOWN_TIMEOUT` | Время на завершение запросов при остановке | `20s` |
| `MAX_IN_FLIGHT` | Предел одновременных запросов | `256` |
| `DATABASE_URL` | Строка подключения рабочей роли | **обязательна** |
| `DB_MAX_CONNS` | Размер пула соединений | `10` |
| `DB_STATEMENT_TIMEOUT` | Таймаут SQL-выражения | `3s` |
| `OIDC_ISSUER` | Ожидаемый издатель токенов | **обязательна** |
| `OIDC_JWKS_URL` | Адрес ключей подписи | **обязательна** |
| `OIDC_AUDIENCE` | Аудитория пользовательских токенов | `sozhiteli-api` |
| `MIGRATE_DATABASE_URL` | Строка подключения роли миграций; только для `migrate` | — |

Дополнительно: Profile — `INTERNAL_HTTP_ADDR` (`:9080`), `INTERNAL_OIDC_AUDIENCE`
(`sozhiteli-internal`); Matching — `PROFILE_INTERNAL_URL`, `OIDC_TOKEN_URL`, `SERVICE_CLIENT_ID`,
`SERVICE_CLIENT_SECRET` (обязательны), `SYNC_INTERVAL` (`5s`), `SYNC_BATCH_SIZE` (`200`);
Interaction — `CONTACT_REQUEST_DAILY_LIMIT` (`20`).

## Правила кода Go

### Обработчики

Образец — `GetQuestionnaire` в `backend/services/profile/internal/api/server.go`.

1. Вызывающего определяет `auth.UserID(ctx)`. Идентификатор пользователя из тела, пути или
   параметров запроса для этого не используется никогда.
2. Успех — сгенерированный тип ответа (`GetMyProfile200JSONResponse{…}`).
3. Ожидаемая неудача — `*problem.Error`: `problem.NotFound`, `problem.Conflict`,
   `problem.Validation`, `problem.TooManyRequests`. Код ошибки должен быть описан в контракте.
4. Любая другая ошибка возвращается как есть, обёрнутая контекстом
   (`fmt.Errorf("load profile: %w", err)`): она станет записью в логе и безличным `500`.
5. Обработчик не пишет в `http.ResponseWriter`, не выставляет статус и не логирует ошибку сам.

### Контекст, таймауты, конкурентность

- `ctx` — первый параметр каждой функции, выполняющей ввод-вывод, и передаётся до драйвера БД и
  HTTP-клиента. ✅ `noctx` запрещает вызовы без контекста.
- `context.Background()` допустим только в `main`, в тестах и для ресурсов, которые должны
  пережить запрос (с комментарием почему).
- Каждый исходящий HTTP-вызов имеет таймаут. `http.DefaultClient` без таймаута не используется.
- Горутину запускает тот, кто может дождаться её завершения и отменить её через `ctx`. Горутин,
  переживающих остановку сервиса, быть не должно.
- Глобальных изменяемых переменных нет. Зависимости передаются через конструкторы.

### Ошибки

- Ошибка либо обрабатывается, либо возвращается с контекстом — никогда не игнорируется молча. ✅ `errcheck`
- Сравнение — `errors.Is` / `errors.As`. ✅ `errorlint`
- `panic` — только для ошибок программиста при инициализации.

### База данных

- Все запросы — SQL-файлы в `internal/store/queries/`, код к ним генерирует sqlc. Составлять SQL
  конкатенацией строк запрещено.
- **Никаких запросов в цикле.** Данные для списка читаются одним запросом; N+1 — дефект.
- Каждый запрос списка имеет `LIMIT` и опирается на индекс; для нового запроса приводится
  `EXPLAIN` в описании изменения, если таблица может вырасти.
- Пагинация — keyset (`WHERE (a, b) < ($1, $2) ORDER BY a DESC, b DESC LIMIT n`), не `OFFSET`.
- Транзакция — короткая; **внутри транзакции нет сетевых вызовов**.
- Несколько изменений, которые должны произойти вместе, — в одной транзакции (`pool.Begin`,
  `queries.WithTx(tx)`, `defer tx.Rollback(ctx)`, `tx.Commit(ctx)`).
- Типы пакета `store` не возвращаются из обработчиков (`API_CONTRACTS.md`).

### Абстракции

- Интерфейс вводится, когда у него есть вторая реализация или он нужен тесту, который иначе
  написать нельзя. «На будущее» интерфейсы не создаются.
- Функция, используемая в одном месте, не выносится в общий пакет.
- В `backend/platform` попадает только то, что нужно **всем** сервисам и не содержит предметной
  области. Сомнение — оставить в сервисе.
- Дублирование 5–10 строк между сервисами предпочтительнее общей зависимости.

### Комментарии и имена

- Код и комментарии в Go — на английском; документация в `docs/` — на русском; комментарии в
  SQL, YAML и TypeScript — на русском.
- Комментарий объясняет **почему**, а не что делает строка. Экспортируемые имена документируются.
- Сгенерированные файлы не редактируются. ✅ `gen:check`

## Правила кода TypeScript

- Backend вызывается только через `useApi()`. ✅ Прямой `fetch` запрещён линтером.
- Типы запросов и ответов берутся из `@sozhiteli/api-client`; вручную не описываются.
- `any` и `@ts-ignore` не используются; `strict` и `noUncheckedIndexedAccess` включены. ✅
- Переменные окружения читаются только в `src/lib/config.ts`.
- Тексты ошибок для пользователя выбираются по `error.code`, а не по `detail`.
- Состояние аутентификации — только через `useAuth()`; токены в компоненты не передаются.
- Новые библиотеки состояния, UI-наборы и роутеры — только по согласованию.
- Web: оформление — классы из `src/app/globals.css`; атрибут `style` запрещён (CSP разрешает
  стили только с nonce, серверная разметка с `style` не применится). ✅ Проверяет линтер.
  Цвет по данным — набор классов (`tone-0…7`), доля — элемент `<meter>`.
- Тексты и вычисления для показа, общие для web и mobile (даты, бюджет, метки совпадений,
  цвет аватара), — в `packages/api-client/src/presentation.ts` с тестами, а не в приложениях.
- Mobile: элементы интерфейса — из `src/components/ui.tsx`; цвета — только из `useTheme()`.

## Миграции

Правила — в `DATA_OWNERSHIP.md`, раздел «Правила изменения схемы». Кратко: новый файл, есть
`Down`, совместима с предыдущей версией сервиса, применённые файлы не редактируются.

## Git

- Одна задача — одна ветка — одно изменение. Задачи из `BACKLOG.md` не объединяются.
- Сообщение коммита: что изменено и зачем, с идентификатором задачи (`P-03: …`).
- Контракт и сгенерированный из него код — в одном коммите.
- В изменение не попадает ничего, чего не требует задача: ни попутный рефакторинг, ни
  переформатирование чужих файлов.

## Определение готовности

Изменение готово, когда:

1. все команды из раздела «Перед сдачей» проходят;
2. новая логика покрыта тестами по `TESTING_STRATEGY.md`;
3. документация соответствует коду: таблица операций в `API_CONTRACTS.md`, переменные окружения
   здесь, состояние задачи в `BACKLOG.md`;
4. в изменении нет функций, которых нет в задаче;
5. в отчёте перечислено, что проверено запуском, а что нет.
