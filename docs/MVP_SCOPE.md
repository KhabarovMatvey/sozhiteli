# Границы MVP

Документ построен по пяти шагам из лекции «MVP и ценность» (S-LEC, слайды 27–34).
Обоснование каждой функции — в `FEATURE_JUSTIFICATION.md`, свидетельства — в `RESEARCH_EVIDENCE.md`.

## Шаг 1. Гипотеза, которую проверяет MVP

**Сегмент:** люди, ищущие человека для совместного поиска и аренды квартиры (сегмент 1).

**JTBD:** когда мне нужно найти человека для совместной аренды жилья, я хочу заранее понять,
насколько совпадают наши обязательные условия и бытовые привычки, чтобы быстрее определять
подходящих кандидатов и не тратить время на заведомо неподходящих.

**Гипотеза MVP:** если пользователь видит обязательные условия и бытовые привычки кандидата в
одинаковом структурированном виде, с явными совпадениями и различиями, ему проще решить,
продолжать ли общение.

**Статус: не подтверждена.** Исследование подтверждает проблемы (см. E-COMPARE-UNEVEN,
E-REPEAT-QUESTIONS, E-LATE-DISCUSS), но решение респондентам не показывали. Гипотеза — предмет
эксперимента, а не установленный факт.

Почему именно она (а не H1, H2, H4, H5 из исследования):

- H3 о бытовых различиях и H4 о несравнимости кандидатов — единственные, у которых есть
  свидетельства от обоих респондентов сегмента 1;
- H1 (верификация, отзывы) исследование прямо не подтвердило как необходимость;
- H2 (разбивка расходов) привязана к конкретной квартире, которой у сегмента 1 на этапе поиска
  соседа ещё нет;
- H5 относится к сегменту 2.

## Шаг 2. Эксперимент

**Что должен сделать пользователь, чтобы гипотеза получила подтверждение:** после просмотра
карточки кандидата со сравнением отправить ему запрос на обмен контактами. Это действие с ценой:
отправитель соглашается показать свой контакт незнакомому человеку.

**Шаги пользователя до конечной точки:**

1. Войти.
2. Заполнить анкету: обязательные условия и ответы о привычках.
3. Указать свой контакт.
4. Открыть выдачу кандидатов, прошедших обязательные условия.
5. Открыть карточку кандидата: совпадения и различия.
6. Отправить запрос на контакт — **конечная точка эксперимента**.
7. Получатель принимает запрос → оба видят контакты и продолжают общение вне сервиса.

**Какие данные собираются** (детали — ADR-0010):

| Факт | Где фиксируется |
|---|---|
| Анкета создана, время создания | Profile, `profile.created_at` |
| Просмотр карточки со сравнением: кто, кого, сколько совпало из скольких | Matching, `candidate_view` |
| Запрос на контакт: кто, кому, когда | Interaction, `contact_request` |
| Ответ на запрос: принят или отклонён, когда | Interaction, `contact_request.status`, `responded_at` |

Сведение данных трёх сервисов для анализа — **ручная выгрузка** (S-LEC, слайд 31: «ручные
процессы — лучше»). Отдельного сервиса аналитики нет.

## Шаг 4. Что отфильтровано

Четыре вопроса фильтра (S-LEC, слайд 33): проверяет ли гипотезу напрямую; необходимо ли для
сценария; можно ли проще; помогает ли измерить.

| Возможность | Решение | Причина |
|---|---|---|
| Встроенный мессенджер | нет | Не проверяет гипотезу. Проще: обмен контактом Telegram/ВК — этими каналами респонденты и пользовались (E-CONTACT-CHANNEL) |
| Верификация личности, отзывы, рейтинги | нет | Исследование прямо не подтвердило необходимость (вывод по H1) |
| Фотографии в анкете | нет в первой итерации | Одно свидетельство (E-PROFILE-EMPTY), где отсутствие фото — лишь часть «пустого профиля». Требует хранилища файлов и модерации. Пустые анкеты исключены иначе: все поля обязательны. Открытый вопрос Q-4 |
| Свободный текст «о себе» | нет | Длинные рассказы мешали сравнению (E-COMPARE-UNEVEN); свободный текст позволяет обойти запрос на контакт и ломает измерение |
| Разбивка расходов, калькулятор стоимости | нет | Относится к конкретной квартире, которой у сегмента 1 ещё нет. Из H2 взято одно: бюджет определён однозначно — без коммунальных (E-COND-BUDGET) |
| Каталог квартир, агрегатор объявлений | нет | Другая задача; не проверяет гипотезу |
| Сбор кандидатов с разных площадок (H4 в исходной формулировке) | нет | Не установлено, что объединение решит проблему. Из H4 взята подтверждённая часть: единый состав сведений о кандидате |
| Сортировка по «совместимости», веса вопросов, рекомендации | нет | Это отдельная гипотеза о ранжировании. Выдача сортируется по свежести анкеты; число совпадений показывается, но не ранжирует |
| Фильтр по районам, справочник районов | нет | Проще: районы свободным текстом, сравнивает человек |
| Сегмент 2 (сосед в свою квартиру) | нет | Другой сегмент и другой сценарий |
| Отмена отправленного запроса, блокировки, жалобы | нет | Не нужны для прохождения сценария; злоупотребления ограничены суточным лимитом |
| Удаление аккаунта из интерфейса | нет, ручная операция | S-LEC: ручной процесс вместо автоматизации. Процедура — `SECURITY.md` |
| Уведомления (email, push) | нет | Усложняют инфраструктуру; в эксперименте входящие запросы видны при открытии приложения. Риск: низкая доля ответов — открытый вопрос Q-5 |
| Платежи, подписки, карты, AI-рекомендации | нет | Не относятся к гипотезе |

## Шаг 5. Критерии успеха и провала

Лекция требует задать пороги заранее (S-LEC, слайд 34). **В материалах исследования порогов нет**,
а придумывать их за команду нельзя: порог — это продуктовое решение. Ниже — метрики и *место для
порогов*; значения утверждает владелец продукта до начала эксперимента (вопрос Q-2).

| Метрика | Как считается | Порог успеха |
|---|---|---|
| M1. Конверсия «просмотр карточки → запрос на контакт» (основная) | доля пар (зритель, кандидат) из `candidate_view`, для которых есть `contact_request` | **не задан — Q-2** |
| M2. Доля принятых запросов | `accepted / (accepted + declined)` среди отвеченных | **не задан — Q-2** |
| M3. Связь решения с совпадениями | сравнение `matched_count / compared_count` для просмотров с запросом и без | качественный вывод |
| M4. Доля дошедших до анкеты | созданные анкеты / зарегистрированные | **не задан — Q-2** |
| K1. Качественный сигнал | интервью с участниками: «помогло ли сравнение решить, писать ли человеку» | **не задан — Q-2** |

M3 — ключевая для гипотезы: если пользователи одинаково часто отправляют запросы при 2 и при 7
совпадениях из 8, сравнение на решение не влияет, и гипотеза не подтверждается даже при высокой M1.
