# План развития под нагрузку

**Главное правило документа: система не «выдерживает N пользователей», пока это не измерено.**
Ниже — допущения, способ их проверки и порядок действий при росте. Число пользователей, на
которое рассчитан продукт, в материалах исследования отсутствует, поэтому целевые значения —
инженерные допущения, а не требования рынка.

## Предварительные SLO

Статус: **допущения**. Утверждаются владельцем продукта перед публичным запуском; до этого служат
порогами нагрузочных сценариев.

| Код | Показатель | Цель | Как измеряется |
|---|---|---|---|
| SLO-A | Доступность: доля ответов без `5xx` | ≥ 99,5 % за 30 дней, по каждому сервису | Логи запросов; позже — метрики |
| SLO-L1 | Задержка чтения на стороне сервиса | p95 ≤ 150 мс, p99 ≤ 400 мс | k6, поле `duration_ms` в логах |
| SLO-L2 | Задержка записи на стороне сервиса | p95 ≤ 250 мс, p99 ≤ 600 мс | то же |
| SLO-F | Свежесть проекции: изменение анкеты видно в Matching | 95 % ≤ 15 с, 99 % ≤ 60 с | `candidate.synced_at − profile_updated_at` |

Целевая интенсивность для проверки фундамента — **50 запросов в секунду на один экземпляр
сервиса**. Это допущение для сценария, а не прогноз.

## Проверка нагрузкой

```bash
npm run infra:up
npm run load:smoke                          # инструмент и среда работают
npm run load:baseline                       # 3 минуты, RATE=50
RATE=200 npm run load:baseline              # другая интенсивность
TARGET=http://matching:8080 npm run load:baseline
```

Сценарии — `tests/load/`. k6 работает в сети сервисов и обращается к сервису напрямую, минуя
edge: измеряется сам сервис, ограничение частоты результат не искажает. Пороги сценария равны
SLO; при превышении k6 завершается с ошибкой.

### Что измерено

Один прогон, 2026-10-13, **ноутбук разработчика** (Intel Core i5-12500H, Docker Desktop: 16
логических ядер и 3,9 ГБ памяти на все контейнеры), сервис Profile, один экземпляр.

| Сценарий | Интенсивность | Запросов | Ошибок | p95 | p99 |
|---|---|---|---|---|---|
| `getQuestionnaire` — JWT, проверка по контракту, без БД | 50 в секунду | 9 002 | 0 | 2,9 мс | 5,8 мс |
| `/readyz` — запрос в PostgreSQL | 10 в секунду | 1 800 | 0 | 2,6 мс | 4,7 мс |

**Что это значит и чего не значит.** Измерены накладные расходы платформы: проверка токена,
проверка запроса по контракту, маршрутизация, сериализация. При 50 запросах в секунду они
занимают единицы миллисекунд — в бюджете SLO-L1 остаётся запас на бизнес-логику. Это **не**
оценка ёмкости системы: продуктовые операции ещё не реализованы, нагрузка мала, стенд не
промышленный, прогон один. Предел пропускной способности не искался.

После реализации продуктовых операций базовый сценарий дополняется выдачей кандидатов, карточкой
и созданием запроса на контакт на базе с реалистичным объёмом данных (задача Q-02). До этого
утверждать что-либо о производительности продукта нельзя.

## Где возникнут узкие места

В порядке ожидаемого появления. Это анализ конструкции, а не результат измерений.

| # | Место | Почему | Как заметить |
|---|---|---|---|
| 1 | **Запрос выдачи Matching** | Идёт по индексу `(city_id, profile_updated_at)` и отбрасывает строки, не прошедшие бюджет, сроки и пол. Если в городе много анкет, а подходит мало, запрос читает почти весь индекс города ради одной страницы | p95 `listCandidates` растёт с числом анкет в городе; `EXPLAIN ANALYZE` показывает много отброшенных строк |
| 2 | **Соединения с PostgreSQL** | `DB_MAX_CONNS` × реплики × сервисы + пул Keycloak (ограничен до 20) должны быть меньше `max_connections` (100 по умолчанию) | Ошибки получения соединения; рост времени ожидания в пуле |
| 3 | **Запись `candidate_view` на каждый просмотр** | Самая частая операция чтения превращается в запись; таблица растёт без ограничения | Доля времени `INSERT` в `getCandidate`; размер таблицы |
| 4 | **Общий экземпляр PostgreSQL** | Тяжёлый запрос одного сервиса отнимает ресурсы у остальных | Задержки Profile и Interaction растут вместе с нагрузкой на Matching |
| 5 | **Синхронизация проекции** | Один поток, строки применяются по одной; при массовом изменении анкет отстаёт | SLO-F; `sync_state.updated_at`; полные страницы подряд |
| 6 | **Keycloak** | Хэширование пароля намеренно дорогое: вход и регистрация нагружают процессор; один экземпляр, JVM | Задержка страницы входа при всплеске регистраций |
| 7 | **Процессор сервисов** | Проверка подписи JWT и проверка запроса по OpenAPI на каждый запрос | Профиль CPU; рост задержки без роста времени в БД |
| 8 | **Edge** | Один экземпляр nginx; лимит по IP общий для пользователей за одним адресом | `429` у добросовестных пользователей; недоступность при отказе экземпляра |

## Этап 1. MVP

**Цель:** провести эксперимент дёшево и просто. Десятки–сотни участников.

| | |
|---|---|
| Развёртывание | Одна машина, Docker Compose; по одному экземпляру каждого сервиса; один PostgreSQL |
| Типичные узкие места | Не ожидаются по нагрузке. Риски — эксплуатационные: единственная машина, отсутствие резервных копий, память под Keycloak |
| Что сделать перед запуском | TLS, промышленный режим Keycloak, секреты, резервное копирование БД с проверкой восстановления (`SECURITY.md`); базовый нагрузочный сценарий на целевой машине |
| Признаки, что пора на этап 2 | Нарушение любого SLO; загрузка процессора или памяти машины устойчиво выше 70 %; число соединений с БД выше половины предела |
| Компромиссы | Нет отказоустойчивости: отказ машины — простой. Нет метрик: наблюдение по логам |

## Этап 2. Первый рост

**Цель:** выдержать рост без изменения архитектуры — настройкой и добавлением экземпляров.

| Признак | Изменение |
|---|---|
| Медленные запросы | `EXPLAIN ANALYZE`, индексы под реальные фильтры. Для выдачи — составной индекс по условиям, которые отсеивают больше всего; `pg_stat_statements` |
| Нагрузка на чтение в Matching | **Реплики Matching.** Сервис не хранит состояния между запросами; синхронизация рассчитана на несколько реплик (сдвиг курсора сравнением) |
| Нехватка соединений | Пересчитать `DB_MAX_CONNS` на реплику; затем PgBouncer в режиме транзакций |
| Влияние сервисов друг на друга в БД | Отдельный экземпляр PostgreSQL для Matching — замена строки подключения (ADR-0003) |
| Отставание проекции | Меньше `SYNC_INTERVAL`, больше `SYNC_BATCH_SIZE`, пакетная запись |
| Рост `candidate_view` | Срок хранения, секционирование по времени |
| Нет видимости | Метрики (Prometheus-формат) и панели: задержки, ошибки, пул соединений, отставание проекции. Это новый компонент — через ADR |
| Отказ машины недопустим | Вторая машина, балансировщик перед edge, управляемый или реплицируемый PostgreSQL |

**Сохраняется:** границы сервисов, контракты, владение данными, механизм ленты, аутентификация,
весь код клиентов.

**Что нужно проверить заранее:** сервисы действительно работают в нескольких экземплярах
(нагрузочный сценарий на двух репликах Matching, задача Q-03).

**Компромиссы:** больше экземпляров — сложнее выкладка и отладка; PgBouncer в режиме транзакций
ограничивает использование сессионных возможностей PostgreSQL.

## Этап 3. Высокая нагрузка

**Цель:** снять ограничения, которые не устраняются настройкой. **Каждое изменение — только по
результатам измерений** и через ADR.

| Измеренная проблема | Возможное изменение | Цена |
|---|---|---|
| Чтение из БД Matching — предел одного узла | Читающие реплики PostgreSQL для запросов выдачи | Задержка репликации складывается с отставанием проекции |
| Запрос выдачи дорог даже с индексами | Иная организация поиска: предрасчёт кандидатов на пользователя, секционирование по городу, специализированный индекс | Сложность, ещё одна модель данных в Matching |
| Одни и те же данные читаются многократно | Кэш: сначала HTTP-кэширование `getQuestionnaire` и справочников; затем кэш в памяти процесса; Redis — последним | Инвалидация, новый компонент |
| Запись `candidate_view` тормозит чтение | Асинхронная запись пакетами | Возможна потеря части фактов при сбое |
| Опроса ленты недостаточно: нужна свежесть в доли секунды или несколько потребителей | Таблица исходящих событий в Profile и брокер сообщений | Новый инфраструктурный компонент и его эксплуатация |
| Keycloak не справляется со входами | Кластер Keycloak или управляемый провайдер | Эксплуатация кластера либо зависимость от поставщика |
| Нужны автоматическое масштабирование и самовосстановление | Оркестратор контейнеров | Существенная операционная сложность |

**Сохраняется:** сервисы и их ответственность, публичные контракты, формат записи ленты,
идемпотентное применение в Matching, правило раскрытия контакта, схема аутентификации.

**Компромиссы:** каждая строка добавляет компонент, который нужно сопровождать. Асинхронность
ослабляет согласованность; кэш добавляет класс ошибок с устаревшими данными.

## Продуктовые операции на 10 000 анкетах (Q-02, Q-03)

2026-10-14, тот же стенд. Данные: 10 000 анкет в одном городе (`npm run load:seed`), 90 % в
статусе «ищу соседа», разные бюджеты, сроки, пол и ответы. Зритель — тестовый пользователь с
анкетой в этом городе.

| Что | Результат |
|---|---|
| Доставка 10 000 новых анкет из Profile в Matching по ленте изменений | 1,7 с после записи |
| Доставка 10 000 удалений | 4,8 с |
| План запроса выдачи | Index Scan по `candidate_feed_idx`, 0,3 мс, читает 50 строк ради 21 |

Нагрузка `npm run load:product`, 3 минуты, 50 запросов в секунду (выдача 60 %, карточка 30 %,
поиск по списку 10 %), один экземпляр Matching:

| Операция | Запросов | Ошибок | p95 | p99 | Порог |
|---|---|---|---|---|---|
| Выдача кандидатов | ≈5 400 | 0 | 6,9 мс | 9,2 мс | SLO-L1 |
| Карточка со сравнением (пишет просмотр) | ≈2 700 | 0 | 66,8 мс | 162 мс | SLO-L2 |
| Карточки по списку | ≈900 | 0 | 7,9 мс | 12 мс | SLO-L1 |

Все пороги выполнены. Карточка заметно медленнее чтения: каждый просмотр — запись в
`candidate_view` с синхронной фиксацией на диск Docker Desktop. Это ожидаемая цена измерения
гипотезы; при росте — пункт 3 таблицы узких мест.

Два экземпляра Matching (`docker compose up --scale matching=2`): синхронизация работает без
ошибок и без дублей (сдвиг курсора сравнением), edge распределил 32 запроса как 19 и 13.

Не проверено: нагрузка на запись запросов на контакт (суточный лимит на пользователя требует
множества тестовых пользователей); долгая работа под нагрузкой; предел пропускной способности.

## Чего этот план не обещает

- Конкретного числа пользователей или запросов в секунду ни на одном этапе.
- Что перечисленных мер этапа 3 хватит: это направления, а не проект.
- Что узкие места появятся в указанном порядке: порядок — предположение до первых измерений.
