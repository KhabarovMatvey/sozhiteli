# Безопасность

Базовая модель безопасности MVP. Система хранит персональные данные (анкеты, контакты), поэтому
правила ниже обязательны для любой задачи. Отступление от них требует архитектурного согласования.

## Что защищаем

| Актив | Где | Чувствительность |
|---|---|---|
| Контакт пользователя | `interaction_db.contact` | **высшая**: прямой способ связаться с человеком |
| Связи между людьми (кто кому писал) | `interaction_db.contact_request` | высокая |
| Анкета | `profile_db.profile`, копия в `matching_db.candidate` | средняя: видна другим вошедшим пользователям по замыслу |
| Учётные данные | Keycloak | высокая; сервисы к ним доступа не имеют |
| Секреты сервисов | переменные окружения | высокая |

## Модель угроз (кратко)

| Угроза | Мера | Где реализовано |
|---|---|---|
| Чтение или изменение чужих данных подменой идентификатора | Идентификатор берётся только из токена; в публичных API нет параметра «чей» | `platform/auth.UserID`, контракты (`/me/…`) |
| Получение чужого контакта без согласия | Контакт отдаётся только в принятом запросе его участникам | ADR-0005, задача I-04 |
| Массовый сбор контактов | Суточный лимит запросов; раскрытие только после принятия получателем | `CONTACT_REQUEST_DAILY_LIMIT`, задача I-02 |
| Перебор и перегрузка API | Ограничение частоты по IP на edge; предел одновременных запросов в сервисе | `deploy/compose/edge`, `httpserver.LimitInFlight` |
| Поддельный или чужой токен | Проверка подписи, издателя, срока и аудитории | `platform/auth`, тест `TestMiddlewareRejectsInvalidTokens` |
| Использование пользовательского токена на внутреннем API | Другая аудитория, роль, отдельный порт без маршрута с edge | ADR-0012, `TestFeedRejectsCallersWithoutServiceRole` |
| SQL-инъекция | Только параметризованные запросы, сгенерированные sqlc | `internal/store` |
| Некорректный и избыточный ввод | Проверка каждого запроса по OpenAPI-схеме до обработчика; предел тела 64 КБ | `platform/openapi`, `httpserver.MaxBody` |
| Утечка данных через логи | В логах нет тел, заголовков, строки запроса и значений полей | `httpserver.AccessLog`, правила ниже |
| Утечка внутренних деталей через ошибки | Непредвиденная ошибка — безличный `500`; причина только в логе | `httpserver.WriteError` |
| Доступ к БД в обход сервисов | PostgreSQL во внутренней сети без опубликованного порта | `compose.yaml`, `infra:smoke` |
| Доступ сервиса к чужой базе | Отдельные базы и роли | ADR-0003, `infra:smoke` |
| Изменение схемы скомпрометированным сервисом | Рабочая роль не имеет прав DDL | `10-databases.sh`, `infra:smoke` |
| Кража токена из браузера (XSS) | Короткий срок токена, ротация refresh-токенов; ограничение признано — см. «Известные ограничения» | ADR-0002 |

## Правило раскрытия контакта

**Контакт человека виден другому пользователю только при одновременном выполнении трёх условий:**

1. существует запрос на контакт между этими двумя людьми;
2. его статус — `accepted`, то есть получатель явно принял запрос;
3. запрашивающий — один из двух участников этого запроса.

Следствия, которые обязана соблюдать любая реализация:

- Открытие карточки кандидата контакт **не раскрывает**: Matching контактов не имеет вовсе.
- Отправка запроса — согласие отправителя показать *свой* контакт получателю, если тот примет.
  Сам запрос контакт получателя не раскрывает.
- У `pending` и `declined` запросов поля `counterpart_contact` в ответе **нет** — ни у одной из сторон.
- Поле заполняется из текущего значения `contact` на момент чтения; в `contact_request` контакты
  не копируются.
- Нет ни одной операции «получить контакт пользователя по идентификатору».
- Отправить и принять запрос может только пользователь с указанным собственным контактом:
  обмен всегда взаимный.

## Защита текстовых полей анкеты

Поля `display_name`, `occupation`, `districts` — свободный текст, в который можно вписать
контакт и обойти правило выше (а заодно — измерение эксперимента). Сервер отклоняет (`422`)
значения, содержащие:

- символ `@`;
- подстроки `http`, `www.`, `t.me`, `vk.com`, `wa.me` без учёта регистра;
- семь и более цифр подряд, считая разделители `пробел`, `-`, `(`, `)`.

Это барьер от простого обхода, а не гарантия. Реализовано: `backend/services/profile/internal/profilerules`.

## Аутентификация и авторизация

- Пароли, регистрация, сброс, защита от перебора — **только Keycloak**. В сервисах нет кода,
  работающего с паролями, и нет собственной криптографии.
- Клиенты — публичные OIDC-клиенты: Authorization Code + PKCE (S256). Implicit flow и вход по
  паролю для них выключены.
- Access token живёт 5 минут; refresh-токены одноразовые (ротация).
- Авторизация в сервисах — по принципу «только своё»: любая операция либо адресована `/me/…`,
  либо проверяет, что вызывающий — участник ресурса. Ролей пользователей нет.
- Web хранит токены в `sessionStorage` вкладки; mobile хранит refresh-токен в защищённом
  хранилище устройства (`expo-secure-store`), access token — в памяти.

## Минимизация данных

| Не собираем | Почему |
|---|---|
| Телефон | Достаточно Telegram или ВК (E-CONTACT-CHANNEL); телефон чувствительнее |
| Точную дату рождения | Для карточки нужен только возраст — хранится год |
| Фотографии | Не включены в MVP (`MVP_SCOPE.md`) |
| Адрес, геолокацию | Район — свободным текстом |
| Паспортные данные | Верификация не входит в MVP |
| Свободный текст «о себе» | Не включён в MVP |
| IP-адреса и user-agent в базах сервисов | Не нужны для сценариев |

В токенах сервисы используют только `sub`, `azp` и роли. Email из токена не читается и в базах
сервисов не хранится.

Регистрация запрашивает только почту и пароль: имя и фамилия удалены из профиля пользователя
realm (K-01, ADR-0013). Имя для карточки человек указывает в анкете и может не совпадать с
паспортным. Политика паролей: не короче 8 символов, не совпадает с почтой.

Демо-анкеты (`npm run demo:seed`) — только для локальной среды: у них нет учётных записей и
контактов, а метрики их исключают по префиксу идентификатора.

## Правила логирования

Разрешено: метод, путь, статус, длительность, `request_id`, `user_id`, имя сервиса, текст
технической ошибки.

**Запрещено** в логах любого уровня:

- тела запросов и ответов, заголовок `Authorization`, токены, cookies;
- значения контактов;
- значения полей анкеты: имя, род занятий, районы, бюджет, ответы о привычках;
- строка запроса (query string);
- строки подключения и секреты.

Тексты ошибок валидации для клиента называют поле и нарушенное правило, но не повторяют значение.

## Секреты и конфигурация

- Секреты приходят только из переменных окружения. В коде и в образах их нет.
- `deploy/compose/.env.example` содержит значения с префиксом `dev-only-`, пригодные
  исключительно для локальной среды; рабочий `.env` в git не попадает.
- У каждого сервиса свой пароль БД. Пароль роли миграций сервису не передаётся.
- Образы сервисов: `distroless`, процесс не от root, без оболочки; контейнеры запускаются с
  файловой системой только для чтения, без привилегий (`cap_drop: ALL`).
- `NEXT_PUBLIC_*` и `EXPO_PUBLIC_*` попадают в клиентские сборки и видны всем: секретов в них
  быть не может.

**Только для локальной разработки** и не должно существовать нигде больше:

- клиент Keycloak `sozhiteli-dev-cli` (вход по паролю без браузера);
- тестовые пользователи из `realm-dev.json`;
- режим `start-dev` Keycloak и HTTP без TLS;
- `compose.dbport.yaml`.

## Требования к промышленной среде

Сборка для одного сервера — `deploy/production/` (2026-10-17). В ней сделано: HTTPS с HSTS на
единственной публичной точке (Caddy, Let's Encrypt); Keycloak в режиме `start` с realm без
dev-клиента и тестовых пользователей; консоль администратора и master realm снаружи закрыты
(доступ через SSH-туннель); случайные пароли в `.env` с правами 600; резервные копии баз с
проверкой восстановления; ограничение частоты запросов по настоящему IP клиента.

Не реализовано:

- подтверждение email и сброс пароля (нужен SMTP);
- секреты из хранилища секретов, а не из файла;
- шифрование диска БД и хранение резервных копий вне сервера (снимки диска или выгрузка);
- TLS между сервисами и PostgreSQL (`sslmode=verify-full`), если БД на отдельном узле;
- правовая сторона обработки персональных данных (согласие, политика, локализация хранения) —
  вне рамок архитектуры, решается владельцем продукта до работы с реальными пользователями.

## Удаление данных пользователя

Ручная операция оператора в MVP. `:id` — идентификатор пользователя.

```sql
-- 1. interaction_db
DELETE FROM contact_request WHERE sender_id = :id OR recipient_id = :id;
DELETE FROM contact WHERE user_id = :id;

-- 2. profile_db — отметку для ленты создаст триггер
DELETE FROM profile WHERE user_id = :id;

-- 3. matching_db — после того как копия анкеты исчезла сама (до интервала синхронизации)
DELETE FROM candidate_view WHERE viewer_id = :id OR candidate_id = :id;
```

Затем удалить учётную запись в консоли Keycloak.

## Известные ограничения

| Ограничение | Риск | Когда устранять |
|---|---|---|
| Токены web-приложения доступны JavaScript страницы | При XSS токен можно украсть на срок его жизни. Смягчено Content-Security-Policy с nonce на каждый запрос (`apps/web/src/proxy.ts`): скрипты и стили только самого приложения (инлайновые `style` тоже запрещены — правило линтера), сетевые запросы только к API и провайдеру входа | При росте требований — перенос токенов на сервер (ADR-0002) |
| Interaction не проверяет существование анкеты получателя | Запросы на несуществующие идентификаторы, ограниченные суточным лимитом | Если появится злоупотребление (ADR-0005) |
| Фильтр контактов в тексте анкеты обходим | Часть пользователей обменяется контактами мимо системы | Не устраняется; учитывается при анализе метрик |
| Ограничение частоты — только по IP | Не различает пользователей за одним адресом | При появлении жалоб или злоупотреблений |
| Контакты хранятся в открытом виде | Раскрытие при компрометации БД | Шифрование диска в промышленной среде; прикладное шифрование — по решению после эксперимента |
| Нет журнала аудита доступа к контактам | Нельзя восстановить, кто что видел, кроме статуса запроса | После эксперимента |
