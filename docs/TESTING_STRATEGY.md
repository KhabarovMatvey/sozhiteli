# Стратегия тестирования

## Уровни

| Уровень | Что проверяет | Зависимости | Команда | Где |
|---|---|---|---|---|
| Юнит | Чистую логику: функции без ввода-вывода | нет | `npm run backend:test`, `npm run test` | `*_test.go` рядом с кодом; `*.test.ts` |
| Контрактный | Ответы сервиса соответствуют OpenAPI; каждая операция защищена и маршрутизируется | поддельный издатель токенов в памяти | `npm run backend:test` | `internal/api/api_test.go` |
| Интеграционный | Работу с настоящим PostgreSQL: миграции, запросы, транзакции, триггеры | временный PostgreSQL в Docker | `npm run backend:test:integration` | `*_integration_test.go`, тег `integration` |
| Сквозной инфраструктурный | Собранные образы, сеть, Keycloak, изоляция БД, синхронизация | запущенная локальная среда | `npm run infra:smoke` | `tools/smoke.mjs` |
| Нагрузочный | Задержки и долю ошибок при заданной интенсивности | запущенная локальная среда | `npm run load:baseline` | `tests/load/` |

Чем ниже уровень, тем больше тестов. Сквозная проверка покрывает **соединение** компонентов, а
не варианты поведения: варианты проверяются ниже.

## Обязательные тесты для новой операции

Каждая задача из `BACKLOG.md`, реализующая операцию, добавляет:

1. **Контрактный тест успеха**: вызвать операцию, проверить статус и
   `openapitest.AssertResponse(t, spec, req, rec)` — ответ соответствует схеме.
2. **Контрактный тест каждого кода ошибки**, который задача реализует (`404`, `409`, `422`, `429`):
   тот же `AssertResponse` и проверка поля `code`.
3. **Тест изоляции пользователей**: действия пользователя A не видны и не доступны пользователю B.
   Для Interaction — отдельно: контакт не появляется в ответе ни при каком статусе, кроме `accepted`.
4. **Интеграционный тест запроса к БД**, если добавлен SQL: на настоящем PostgreSQL через
   `pgtest.NewDatabase(t)`.
5. **Юнит-тесты чистой логики** (валидация, сравнение, расчёт) — табличные, включая границы.
6. Смену пометки `x-implementation-status` на `implemented`: существующий тест начнёт проверять,
   что операция больше не отвечает `501`.

Образцы: `backend/services/profile/internal/api/api_test.go` (контрактный),
`backend/services/profile/internal/internalapi/feed_integration_test.go` (интеграционный с
настоящими токенами и базой).

## Правила написания тестов

- Тест проверяет поведение через публичный вход (HTTP-обработчик, экспортируемую функцию), а не
  внутреннее устройство.
- **Базу данных не подменяют.** Код, работающий с SQL, тестируется на PostgreSQL. Моки хранилища
  не пишутся: они проверяют мок, а не запрос.
- Токены в тестах — настоящие JWT от `authtest.NewIssuer(t)`; проверка токена в тестах не отключается.
- Тесты независимы и не полагаются на порядок: у каждого интеграционного теста своя пустая база.
- Имя теста формулирует свойство: `TestSyncIsIdempotentAndIgnoresStaleVersions`.
- `time.Sleep` для ожидания события не используется, кроме случаев, где ожидание — предмет теста.
- **Лента изменений в тестах.** Горизонт ленты общий для всего сервера PostgreSQL, а пакеты
  тестов выполняются параллельно: открытая транзакция соседнего теста на мгновение задерживает
  появление записи в ленте. Тест, читающий ленту сразу после записи, сначала вызывает
  `awaitFeedHorizon` (образец — `feed_integration_test.go`). Это свойство механизма (ADR-0004),
  а не нестабильность.
- Тест, упавший один раз из десяти, — дефект, а не «нестабильность окружения».
- Тесты не удаляются и не ослабляются ради прохождения CI. Тест мешает задаче — это вопрос к
  постановщику задачи.

## Что не тестируется автоматически

| Что | Почему | Чем заменено |
|---|---|---|
| Экраны web в браузере | Нет инструмента браузерных тестов (новая зависимость требует согласования) | Ручная проверка по сценарию из `VERIFICATION.md`; e2e-тесты — задача Q-01 |
| Экраны mobile после входа | Нет эмулятора; в браузере вход идёт через всплывающее окно, а панель проверки их блокирует | Типы, линтер, `expo-doctor`, сборка бандлов Android и web; ручная проверка на устройстве — MB-00 |
| Вход в мобильном приложении на устройстве | Нужен эмулятор или устройство | Проверка типов, линтер, `expo-doctor`, сборка бандла; ручная проверка — задача MB-00 |
| Поведение под промышленной нагрузкой | Нет промышленного стенда | Базовый сценарий k6 локально; `SCALING_PLAN.md` |
| Выполнение CI на GitHub | Репозиторий ещё не опубликован | Файл проверен `actionlint`; те же команды выполнены локально |

## CI

`.github/workflows/ci.yml`, четыре независимые задачи:

| Задача | Проверяет |
|---|---|
| `contracts` | Контракты валидны; сгенерированный код соответствует контрактам и SQL |
| `backend` | Формат, `go mod tidy`, сборка, `vet`, линтер, все тесты с детектором гонок на PostgreSQL |
| `images` | Образы собираются, среда поднимается, сквозная проверка проходит |
| `clients` | Формат, линтер, типы, тесты, сборка web, `expo-doctor`, сборка бандла mobile |

Изменение не принимается при красном CI. Отключать задачи и проверки запрещено.
