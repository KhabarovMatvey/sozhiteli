# ADR-0001. Разбиение на сервисы: Profile, Matching, Interaction

Статус: принято · 2026-10-13

## Контекст

Задание жёстко запрещает монолит, модульный монолит и распределённый монолит и одновременно
требует минимального разумного числа сервисов, каждый — с обоснованной ответственностью.
Предварительные области: Profile, Matching/Discovery, Interaction, Identity.

Честная исходная позиция: **из исследования и из нагрузки необходимость нескольких сервисов не
следует.** Эксперимент на десятках пользователей проще обслужить одним приложением. Отказ от
монолита — внешнее ограничение, и в документации оно называется ограничением, а не выводом.

Поэтому вопрос решения другой: *раз сервисов должно быть несколько, где провести границы, чтобы
они были настоящими, а число сервисов — наименьшим.*

## Альтернативы

**A. Два сервиса: Profile и «Matching + Interaction».** Меньше развёртываний. Но объединяются
части с противоположными свойствами: вычислительное чтение чужих анкет и транзакционная работа с
самыми чувствительными данными. Изменение алгоритма подбора выкатывалось бы вместе с кодом,
раскрывающим контакты.

**B. Два сервиса: «Profile + Matching» и Interaction.** По данным это самое естественное
объединение: Matching читает ровно то, что пишет Profile, и проблема проекции исчезает. Но тогда
первый сервис содержит почти весь продукт, второй — небольшой придаток. По сути это монолит с
вынесенной таблицей, то есть то, что задание запрещает.

**C. Три сервиса: Profile, Matching, Interaction.** *(выбрано)*

**D. Четыре и более: отдельно анкета привычек, справочники, аналитика, уведомления.** У этих
частей нет ни собственных данных с отдельным жизненным циклом, ни отдельной нагрузки. Сервисы
ради количества.

**E. Собственный сервис Identity.** Отклонено в ADR-0002: готовый OIDC-провайдер.

## Решение

Три сервиса собственной разработки и готовый провайдер идентификации:

| Сервис | Ответственность |
|---|---|
| Profile | Источник истины для анкет |
| Matching | Подбор и сравнение на собственной копии анкет |
| Interaction | Контакты и согласие на их раскрытие |

Критерии, по которым проведена граница, — каждый сервис отличается от двух других по всем трём:

| | Profile | Matching | Interaction |
|---|---|---|---|
| Причина изменений | состав анкеты | алгоритм подбора | правила согласия |
| Нагрузка | редкая запись | частое чтение, растёт с числом просмотров | редкая транзакционная запись |
| Чувствительность данных | средняя | средняя (копия) | высшая |

Зависимости: только Matching → Profile, фоновая (ADR-0004). Interaction независим. Циклов нет.

Признаки, что сервисы настоящие, а не распределённый монолит, — и все они проверяются:

- отдельные базы и роли, чужие таблицы недоступны физически (ADR-0003);
- отдельные Go-модули и образы, общий код — только технический (ADR-0008);
- ни один пользовательский запрос не требует участия двух сервисов;
- каждый сервис остаётся полезным при отказе остальных (`ARCHITECTURE.md`, модель отказов);
- сервисы развёртываются и масштабируются по отдельности.

## Почему так

- Вариант B нарушает ограничение задания по существу; вариант A смешивает риски.
- Matching — единственная часть, чья нагрузка растёт быстрее числа пользователей (каждый
  пользователь просматривает многих), и единственная, которую будут переписывать при развитии
  алгоритма. Отдельное масштабирование и отдельный цикл выпуска здесь реальны.
- Interaction хранит контакты. Сервис, который один знает контакты и один решает, когда их
  показать, — наименьшая возможная поверхность для ошибки, раскрывающей чужой контакт.

## Недостатки

- **Сложнее, чем нужно эксперименту:** три развёртывания, три базы, три набора миграций.
- Проекция в Matching — дополнительный движущийся механизм и согласованность «в конечном счёте».
- Экраны, которым нужны данные двух сервисов, соединяет клиент: больше запросов с устройства.
- Сведение метрик эксперимента требует выгрузки из трёх баз (ADR-0010).
- Удаление данных пользователя затрагивает три сервиса и в MVP выполняется вручную.

## Условия пересмотра

- Появилась операция, которая должна атомарно изменить данные двух сервисов → граница проведена
  неверно, пересмотреть.
- Два сервиса устойчиво меняются и выкатываются только вместе → кандидаты на объединение.
- Сегмент 2 принесёт сущность «жильё» со своим жизненным циклом → рассмотреть отдельный сервис,
  но не раньше, чем появится подтверждённая функция.
- Ограничение «не монолит» снято → вариант B становится допустимым и более дешёвым.
