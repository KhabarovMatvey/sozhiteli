# ADR-0002. Идентификация: Keycloak, OIDC, публичные клиенты с PKCE

Статус: принято · 2026-10-13

## Контекст

Нужны регистрация и вход для web, Android и iOS. Требования: готовое OIDC-совместимое решение,
никакой собственной криптографии, запуск локально одной командой, одинаковая схема для всех клиентов.

## Альтернативы

**Провайдер**

| Вариант | Оценка |
|---|---|
| Собственный сервис Identity | Отклонено: хранение паролей, сброс, защита от перебора — класс задач, где ошибки дороже всего |
| Облачный провайдер (Auth0, Clerk и подобные) | Данные пользователей у третьей стороны за рубежом; среда не воспроизводится без сети и учётной записи |
| Ory Kratos + Hydra | Без готовых страниц входа: пришлось бы писать собственный интерфейс регистрации |
| Dex | Федерация внешних провайдеров; своей регистрации пользователей нет |
| Zitadel | Сопоставим по возможностям; сложнее первичная настройка, меньше готовых примеров импорта конфигурации |
| **Keycloak** | Зрелый, страницы входа и регистрации из коробки, декларативный импорт realm из файла, PKCE, client credentials, роли |

**Схема для web**

| Вариант | Оценка |
|---|---|
| Сервер Next.js хранит токены, браузер получает cookie (BFF) | Наиболее защищённый: токен недоступен JavaScript. Но появляется серверная часть с сессиями, а схема для web и mobile становится разной |
| **Публичный клиент в браузере, Authorization Code + PKCE** | Одна схема для web и mobile; web остаётся статическим приложением. Токен доступен JavaScript страницы |

## Решение

1. Провайдер — **Keycloak**, realm `sozhiteli`. Локально — `start-dev` с импортом
   `deploy/compose/keycloak/realm-dev.json`.
2. Web и mobile — **публичные клиенты**, поток Authorization Code + PKCE (S256). Implicit flow и
   вход по паролю выключены. Web — `oidc-client-ts`, mobile — `expo-auth-session`.
3. Access token — JWT на 5 минут; refresh-токены одноразовые.
4. **Каждый сервис проверяет токен сам** по закэшированным ключам (`platform/auth`, go-oidc):
   подпись, `iss`, `exp`, `aud = sozhiteli-api`. Сетевого обращения к Keycloak на запрос нет.
5. Идентификатор пользователя во всех сервисах — claim `sub` (UUID).
6. Адрес издателя и адрес ключей настраиваются раздельно (`OIDC_ISSUER`, `OIDC_JWKS_URL`): в
   сети контейнеров Keycloak доступен по другому имени, чем в токене.

## Почему так

- Проверка токена в сервисе, а не на edge: сервис защищён, даже если к нему обратились в обход
  edge, и не зависит от доверия к сети.
- Локальная проверка подписи: Keycloak не становится узким местом и точкой отказа для каждого запроса.
- Одна схема для двух клиентов: один раздел документации и один образец кода для следующих исполнителей.
- Публичный клиент для web — осознанный компромисс MVP: риск ограничен пятиминутным сроком
  токена и ротацией refresh-токенов.

## Недостатки

- Keycloak — самый тяжёлый компонент среды (JVM, сотни мегабайт памяти, старт десятки секунд).
- В браузере токен доступен JavaScript: XSS даёт злоумышленнику токен на срок его жизни.
- Отозвать уже выданный access token нельзя до истечения пяти минут.
- `user_id` привязан к формату `sub` Keycloak; смена провайдера потребует таблицы соответствия.
- Форма регистрации по умолчанию просит имя и фамилию, которые системе не нужны (задача K-01).

## Условия пересмотра

- Публичный запуск с реальными пользователями → сначала CSP (W-05); затем оценить перенос
  токенов web на сервер (вариант BFF).
- Потребуется мгновенный отзыв доступа → короче срок токена или проверка статуса сессии.
- Вход через сторонние учётные записи (VK ID, Telegram) → подключается в Keycloak как внешний
  провайдер, сервисы не меняются.
- Эксплуатация Keycloak окажется непосильной для команды → управляемый OIDC-провайдер; сервисам
  достаточно сменить три переменные окружения.
