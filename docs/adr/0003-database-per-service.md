# ADR-0003. Изоляция данных: один экземпляр PostgreSQL, отдельная база и роли на сервис

Статус: принято · 2026-10-13

## Контекст

Сервисы не должны иметь доступа к чужим таблицам. При этом для локальной среды и MVP допустим
один физический экземпляр PostgreSQL, если логическая изоляция обеспечена.

## Альтернативы

| Вариант | Оценка |
|---|---|
| Одна база, общая схема, договорённость «не трогать чужое» | Изоляция только на словах; первый же `JOIN` «для удобства» создаёт распределённый монолит |
| Одна база, схема на сервис, права по ролям | Изоляция реальна, но запрос между схемами написать можно: достаточно ошибки в правах |
| **Один экземпляр, отдельная база на сервис, отдельные роли** | Запросов между базами в PostgreSQL нет вообще: чужую таблицу нельзя прочитать даже при ошибке в правах |
| Отдельный экземпляр PostgreSQL на сервис | Та же логическая изоляция плюс изоляция ресурсов; втрое больше памяти и операций — для MVP избыточно |

## Решение

Один экземпляр PostgreSQL 18. Для каждого сервиса:

- база `<service>_db`;
- роль `<service>_migrator` — владелец схемы, используется только командой `migrate`;
- роль `<service>_app` — рабочая роль сервиса: `SELECT`, `INSERT`, `UPDATE`, `DELETE`, без DDL;
- у `PUBLIC` отозвано право подключения к базе.

Сервис получает строку подключения только своей рабочей роли к своей базе. Keycloak — отдельная
база `keycloak_db`. Создание — `deploy/compose/postgres/init/10-databases.sh`.

PostgreSQL находится во внутренней сети Compose без выхода наружу; порт на хосте не публикуется.

## Почему так

- Граница проверяется сервером БД, а не ревью кода: `profile_app` получает отказ уже при попытке
  подключиться к `matching_db`. Проверка включена в `npm run infra:smoke`.
- Разделение ролей миграций и работы: уязвимость в сервисе не позволяет изменить схему.
- Переход к отдельным серверам БД — замена строки подключения, код не меняется.

## Недостатки

- Общие ресурсы: тяжёлый запрос одного сервиса замедляет остальные; общий предел `max_connections`.
- Одна точка отказа для всех сервисов.
- Идентификаторы транзакций общие на экземпляр: долгая транзакция в любой базе задерживает ленту
  изменений Profile (ADR-0004).
- Отчёт по данным двух сервисов нельзя получить одним SQL-запросом (ADR-0010).

## Условия пересмотра

- Сумма пулов соединений всех реплик приближается к `max_connections` → пул соединений
  (PgBouncer) или отдельные экземпляры.
- Нагрузка одного сервиса заметно влияет на задержки другого → отдельный экземпляр для него.
- Разные требования к резервному копированию или размещению данных у разных сервисов.
