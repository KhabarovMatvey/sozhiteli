# ADR-0004. Данные для Matching: локальная проекция по ленте изменений

Статус: принято · 2026-10-13

## Контекст

Matching фильтрует и сравнивает анкеты, которыми владеет Profile, но доступа к базе Profile у
него нет (ADR-0003). Нужно решить, откуда Matching берёт данные кандидатов.

Ограничения: не добавлять брокер сообщений без необходимости; не вызывать сервис при обработке
пользовательского запроса; механизм должен переживать отказ любой из сторон и допускать развитие
под нагрузкой.

## Альтернативы

| Вариант | Как работает | Оценка |
|---|---|---|
| Синхронный запрос к Profile на каждый запрос выдачи | Matching просит у Profile отфильтрованных кандидатов | Фильтрацию тогда выполняет Profile, а Matching — пустая прослойка; выдача недоступна при отказе Profile; задержки складываются |
| Пакетное получение на каждый запрос | Matching запрашивает у Profile анкеты по списку идентификаторов | Список кандидатов всё равно нужно откуда-то взять; та же зависимость по доступности |
| Периодическая полная выгрузка | Раз в N минут Matching забирает все анкеты | Просто, но объём растёт линейно с числом анкет, а свежесть — минуты |
| **Локальная проекция + опрос ленты изменений по HTTP** | Profile отдаёт изменившиеся анкеты после курсора; Matching применяет их к своей таблице | Брокер не нужен; зависимость фоновая; объём пропорционален числу изменений |
| Локальная проекция + брокер сообщений | Profile публикует события, Matching подписан | То же самое плюс новый инфраструктурный компонент и задача «записать в БД и опубликовать атомарно» |
| Логическая репликация PostgreSQL | Таблица Profile реплицируется в базу Matching | Связывает сервисы схемой БД: любое изменение таблицы Profile ломает Matching в обход контракта |

## Решение

**Локальная проекция, обновляемая опросом ленты изменений.**

Profile, внутренний API (порт 9080, `profile-internal.v1.yaml`):

```
GET /internal/v1/profile-changes?cursor=<непрозрачный>&limit=200
→ { items: [{ user_id, version, deleted, profile? }], next_cursor }
```

Matching (`internal/projection`): фоновый цикл раз в `SYNC_INTERVAL` читает страницу и в **одной
транзакции** применяет её к таблице `candidate` и сдвигает курсор в `sync_state`.

### Как лента не теряет изменения

Наивный курсор по времени или по счётчику теряет записи: транзакция, начавшаяся раньше, может
зафиксироваться позже, и её строка окажется «позади» уже прочитанной позиции.

Решение:

1. Версия строки — идентификатор записавшей её транзакции: триггер `profile_touch` выставляет
   `feed_version = pg_current_xact_id()` при каждой вставке и обновлении.
2. Лента отдаёт только строки с версией **меньше горизонта** — самого старого идентификатора
   среди ещё не завершённых транзакций (`pg_snapshot_xmin(pg_current_snapshot())`).

Все транзакции с идентификатором ниже горизонта уже завершены, значит строк с меньшей версией
больше не появится. Потребитель, дошедший до курсора ниже горизонта, ничего не пропустил.

Свойство закреплено тестом `TestFeedNeverSkipsChangesOfSlowTransactions`: строка быстрой
транзакции не отдаётся, пока открыта более старая медленная, а после её фиксации отдаются обе.

Удаление: триггер `profile_record_deletion` записывает отметку в `profile_deletion`; лента
объединяет изменения и отметки в общем порядке версий.

Приложению Profile ничего делать не нужно: версии и отметки ставят триггеры. Забыть обновить
ленту при реализации новой операции невозможно.

### Гарантии

| Свойство | Значение |
|---|---|
| Доставка | at-least-once: повторы возможны, пропуски — нет |
| Содержимое | Текущее состояние анкеты, а не история: промежуточные состояния могут быть не видны |
| Идемпотентность | `UPSERT … WHERE source_version <= EXCLUDED.source_version`; удаление с тем же условием |
| Несколько реплик Matching | Курсор сдвигается сравнением с прежним значением: страницу фиксирует ровно одна реплика |
| Задержка в норме | До `SYNC_INTERVAL` (5 с по умолчанию) |
| Отказ Profile или Keycloak | Проекция не обновляется, выдача работает; повторы с паузой до 1 минуты |
| Нарушение контракта в записи | Страница не применяется, курсор не двигается, ошибка в логе: остановка, а не молчаливая потеря |

Чтение своих условий: Matching берёт анкету самого пользователя из той же проекции. Если её там
ещё нет, операция отвечает `409 profile_not_ready` с `Retry-After`.

## Почему так

- Единственный вариант без брокера, при котором Matching не зависит от Profile в момент запроса.
- Matching владеет своей моделью чтения: может добавлять индексы и вычисляемые столбцы, не
  затрагивая Profile.
- Формат ленты не зависит от способа доставки: замена опроса на брокер не меняет ни запись
  ленты, ни код применения в Matching.

## Недостатки

- Согласованность в конечном счёте: изменённая анкета появляется в выдаче с задержкой.
- Данные анкет хранятся дважды.
- **Долгая открытая пишущая транзакция в экземпляре PostgreSQL задерживает ленту** (горизонт не
  двигается). Данные не теряются, но свежесть страдает. Смягчение:
  `idle_in_transaction_session_timeout` в пуле соединений сервисов.
- Опрос создаёт фоновую нагрузку даже без изменений: один лёгкий запрос на реплику раз в интервал.
- Отметки об удалении накапливаются в `profile_deletion`.
- Нарушение контракта останавливает синхронизацию до вмешательства человека.

## Развитие под нагрузкой

| Признак | Изменение | Что сохраняется |
|---|---|---|
| Отставание проекции стабильно выше SLO при пустых страницах | Уменьшить `SYNC_INTERVAL` | Всё |
| Отставание растёт при полных страницах | Увеличить `SYNC_BATCH_SIZE`; пакетная запись вместо построчной | Контракт |
| Нужна свежесть заметно меньше секунды или появился второй потребитель | Таблица исходящих событий в Profile + брокер | Формат записи, идемпотентное применение |
| Фоновая нагрузка опроса заметна на Profile | Длинный опрос или уведомление `LISTEN/NOTIFY` как сигнал «есть изменения» | Контракт, курсор |
| Объём `profile_deletion` мешает | Удаление отметок старше срока, заведомо большего максимального отставания потребителей | Контракт |

## Условия пересмотра

- Второй сервис-потребитель ленты.
- Требование показывать изменение анкеты в выдаче немедленно.
- Невозможность удерживать пишущие транзакции короткими.
