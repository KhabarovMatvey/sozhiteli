# ADR-0006. Edge-прокси без логики; API Gateway и BFF не вводятся

Статус: принято · 2026-10-13

## Контекст

Клиенты обращаются к трём сервисам. Задание разрешает API Gateway или BFF только при конкретном
обосновании.

## Альтернативы

| Вариант | Оценка |
|---|---|
| Клиенты обращаются к сервисам напрямую, без общего входа | Три публичных адреса, три набора настроек CORS и TLS; ограничение частоты нужно реализовать в каждом сервисе; каждый сервис выставлен наружу |
| **Обратный прокси: только транспорт** | Один адрес, одна точка TLS, CORS и ограничения частоты; логики нет |
| API Gateway с проверкой токенов и политиками | Проверка токена только на шлюзе делает сервисы беззащитными при обращении в обход; дублировать проверку — усложнение без выигрыша |
| BFF, собирающий ответы для экранов | Нужен, когда экран требует данных нескольких сервисов и клиент не может собрать их сам. Сейчас таких экранов два, и каждому достаточно двух параллельных вызовов |

## Решение

Один **nginx** как edge-прокси (`deploy/compose/edge/default.conf.template`):

- маршрутизация по префиксу: `/api/profile/` → Profile, `/api/matching/` → Matching,
  `/api/interaction/` → Interaction; префикс отрезается;
- CORS для одного разрешённого источника (`WEB_ORIGIN`), ответ на preflight;
- ограничение частоты по IP: 20 запросов в секунду, всплеск 40;
- собственные ошибки (`429`, `502`–`504`, `404`) — в едином формате `problem+json`;
- предел тела запроса 64 КБ.

Конкретные причины его существования:

1. PostgreSQL и внутренний порт Profile остаются во внутренних сетях; наружу опубликован один порт.
2. Web и mobile получают один базовый адрес API.
3. Ограничение частоты и CORS настраиваются в одном месте.
4. В промышленной среде это место завершения TLS.

Edge **не делает**: не проверяет и не читает токены, не объединяет ответы, не кэширует, не
содержит правил продукта, не маршрутизирует во внутренний API.

## Почему так

- Причины 1–4 — транспортные, и решаются стандартным прокси без единой строки своего кода.
- Соединение данных на клиенте дешевле BFF, пока экранов с данными двух сервисов мало: BFF — это
  ещё один сервис, знающий обо всех остальных, то есть связывающий их.
- nginx: ограничение частоты встроено, конфигурация статическая, образ мал.

## Недостатки

- Ещё один компонент и единая точка отказа периметра.
- Ограничение частоты только по IP: пользователи за одним адресом делят лимит.
- Экраны с данными двух сервисов делают несколько запросов с устройства.
- Формат ошибок edge поддерживается вручную в конфигурации и должен совпадать с форматом сервисов.

## Условия пересмотра

- Появляется экран, которому нужно три и более последовательных вызова, а задержка на мобильной
  сети мешает пользователям → рассмотреть BFF для этого клиента.
- Нужны лимиты на пользователя, а не на адрес → лимит в сервисе по `sub` (уже так сделан
  суточный лимит запросов на контакт).
- Развёртывание в среде, где маршрутизацию даёт платформа (ingress) → nginx заменяется её
  средствами, сервисы не меняются.
