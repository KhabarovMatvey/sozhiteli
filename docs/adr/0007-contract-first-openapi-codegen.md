# ADR-0007. Контракт прежде кода: OpenAPI и кодогенерация

Статус: принято · 2026-10-13

## Контекст

Отдельные функции будут реализовывать разные исполнители, в том числе менее опытные,
параллельно в backend, web и mobile. Нужно, чтобы никто не придумывал собственные адреса, поля и
коды ошибок и чтобы расхождение между сервером и клиентом обнаруживалось до запуска.

## Альтернативы

| Вариант | Оценка |
|---|---|
| Код первичен, описание API генерируется из него | Контракт появляется после реализации: клиентская задача не может начаться раньше серверной, а форма API определяется тем, как удобнее было написать обработчик |
| Контракт в документе, типы пишутся вручную с обеих сторон | Расхождения неизбежны и находятся только при интеграции |
| **OpenAPI — источник истины; сервер, клиент и проверка запросов генерируются** | Расхождение становится ошибкой компиляции или красным CI |
| gRPC и protobuf | Строгие контракты, но для браузера нужен дополнительный слой; задание предпочитает REST |

## Решение

1. Контракты — `contracts/openapi/*.yaml`, **OpenAPI 3.0.3** (не 3.1: oapi-codegen v2 полностью
   поддерживает 3.0).
2. Сервер Go — `oapi-codegen` в режиме **strict server**: каждой операции соответствует метод
   интерфейса `StrictServerInterface` с типизированными запросом и ответом.
3. Проверка запросов — middleware на основе `kin-openapi` (`platform/openapi`): запрос сверяется
   со встроенной в сервис спецификацией **до** обработчика.
4. Клиент TypeScript — `openapi-typescript` (типы) и `openapi-fetch` (вызовы), пакет
   `@sozhiteli/api-client`, общий для web и mobile.
5. Клиент Matching к внутреннему API Profile генерируется из того же файла, что и сервер Profile.
6. Сгенерированный код **коммитится**. CI (`gen:check`) падает, если он не соответствует контрактам.
7. Состояние операции — расширение `x-implementation-status`; нереализованная операция отвечает
   `501`, что проверяется тестом.
8. Ошибки — единый формат RFC 9457 (`platform/problem`).

## Почему так

- Полный контракт существует до бизнес-логики: задачи backend и клиентов по одной операции
  независимы и могут выполняться параллельно.
- Strict server не даёт вернуть ответ произвольной формы: исполнитель заполняет типизированную
  структуру, остальное проверяет компилятор.
- Проверка по спецификации убирает из обработчиков ручные проверки типов, длин и перечислений:
  правило записано один раз, в контракте.
- Коммит сгенерированного кода: сборка не зависит от генераторов, а изменения API видны в diff.
- `501` вместо отсутствующего маршрута: клиент получает осмысленную ошибку, а список оставшихся
  работ читается прямо из контракта.

## Недостатки

- Спецификация встроена в бинарник и разбирается при старте; проверка каждого запроса стоит
  процессорного времени (измерено в базовом сценарии k6, `SCALING_PLAN.md`).
- Режим strict порождает много типов; сгенерированные файлы велики.
- Схема `Problem` повторена в каждом контракте.
- Генераторам нужны Go, Node.js и Docker (sqlc запускается из образа).
- oapi-codegen переименовывает `operationId` в стиле Go во встроенной спецификации —
  учитывается в `openapitest`.
- OpenAPI 3.0: нет части возможностей 3.1.

## Условия пересмотра

- Стоимость проверки запросов станет заметной в профиле под нагрузкой → отключать проверку для
  отдельных горячих операций, сохранив её в тестах.
- oapi-codegen получит полную поддержку 3.1 и потребуются её возможности.
- Появятся потоковые или двунаправленные взаимодействия → отдельное решение о протоколе.
