# ADR-0008. Monorepo: отдельный Go-модуль на сервис и техническая библиотека platform

Статус: принято · 2026-10-13

## Контекст

Задание предпочитает monorepo с независимо развёртываемыми сервисами и запрещает общую
библиотеку с бизнес-логикой. При этом трём сервисам нужен одинаковый технический каркас:
жизненный цикл HTTP-сервера, проверка токенов, формат ошибок, пул соединений, миграции.

## Альтернативы

**Модули Go**

| Вариант | Оценка |
|---|---|
| Один модуль, три каталога `cmd/` | Проще всего, один `go.mod`. Но независимость сервисов держится только на дисциплине, а версии зависимостей общие для всех |
| **Отдельный модуль на сервис + модуль `platform`** | Сервис физически не может импортировать код другого: его нет в `go.mod` и в контексте сборки образа |
| Отдельный репозиторий на сервис | Максимальная независимость; контракты, документация и изменение на стыке сервисов расползаются по репозиториям — плохо для небольшой команды и для исполнителей отдельных задач |

**Общий код**

| Вариант | Оценка |
|---|---|
| Никакого общего кода, каркас скопирован в каждый сервис | Полная независимость; три копии кода безопасности, которые разойдутся при первом же исправлении |
| **Общая техническая библиотека без предметной области** | Одна реализация проверки токенов и формата ошибок; риск превращения в свалку — контролируется правилом |
| Общая библиотека с доменными типами | Запрещено заданием: связывает сервисы общей моделью |

**Клиентская часть:** npm workspaces — менеджер пакетов уже есть вместе с Node.js; отдельный
инструмент оркестрации для трёх пакетов не нужен.

## Решение

```
backend/platform            модуль sozhiteli.internal/platform
backend/services/profile    модуль sozhiteli.internal/profile
backend/services/matching   модуль sozhiteli.internal/matching
backend/services/interaction модуль sozhiteli.internal/interaction
backend/tools               модуль с версиями инструментов кодогенерации
```

- Сервис подключает `platform` директивой `replace` на относительный путь. `backend/go.work`
  существует только для редактора; сборка образов идёт с `GOWORK=off`.
- Контекст сборки образа сервиса — `backend/`, но Dockerfile копирует только `platform/` и
  каталог своего сервиса.
- **Правило `platform`:** только код, который нужен всем сервисам и не знает предметной области.
  Сейчас: `app`, `auth`, `config`, `health`, `httpserver`, `logging`, `migrate`, `openapi`,
  `postgres`, `problem`. Слов «анкета», «кандидат», «контакт» там нет и быть не должно.
- Скрипты — на Node.js (`tools/*.mjs`), запуск через `npm run`: одинаково в Windows, macOS, Linux и CI.
- Клиенты: npm workspaces `apps/*`, `packages/*`; общий код клиентов — только
  `@sozhiteli/api-client`, без компонентов интерфейса. С 2026-10-14 в нём, кроме вызовов API,
  лежат чистые функции представления значений контракта (`presentation.ts`: тексты ошибок по
  кодам, форматирование дат, сумм и контактов), чтобы web и mobile говорили с пользователем
  одинаково.

## Почему так

- Граница между сервисами проверяется компилятором и сборкой образа, а не ревью.
- Проверка токенов, формат ошибок и защита от перегрузки существуют в одном экземпляре:
  исправление уязвимости делается один раз.
- Monorepo: контракт, сервер, клиент и документация меняются одним изменением и видны исполнителю целиком.
- Node.js-скрипты: `make` в Windows отсутствует, а Node.js и так обязателен для клиентов.

## Недостатки

- Изменение `platform` затрагивает все сервисы и требует пересборки всех образов.
- Несколько `go.mod`: версии общих зависимостей нужно держать согласованными вручную.
- `platform` — естественное место, куда хочется положить «общее» доменное; правило нужно соблюдать.
- Для запуска Go-команд нужен Node.js.
- У сервисов нет независимых номеров версий; образ помечается идентификатором коммита.

## Условия пересмотра

- Сервисам потребуются разные версии `platform` одновременно → версионирование модуля и публикация.
- Разные команды с разным ритмом выпуска → разделение репозиториев; модули к этому готовы.
- Число пакетов клиентской части вырастет настолько, что сборка без кэша задач станет медленной →
  инструмент оркестрации.
