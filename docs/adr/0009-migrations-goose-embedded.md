# ADR-0009. Миграции: goose, SQL-файлы в бинарнике, отдельный шаг и отдельная роль

Статус: принято · 2026-10-13

## Контекст

У каждого сервиса своя схема. Миграции должны выполняться воспроизводимо, не ломать работающую
версию сервиса и не давать работающему сервису прав на изменение схемы.

## Альтернативы

**Инструмент**

| Вариант | Оценка |
|---|---|
| golang-migrate | Распространён; пара файлов на миграцию; отдельный образ CLI |
| **goose** | Один файл с секциями `Up` и `Down`; работает как библиотека со встроенными файлами; формат понимает sqlc |
| Atlas | Декларативный, мощный; избыточен для трёх небольших схем |
| ORM с автомиграцией | Схема выводится из кода и меняется неявно — несовместимо с подходом «SQL первичен» |

**Когда выполнять**

| Вариант | Оценка |
|---|---|
| При старте сервиса | Реплики стартуют одновременно и соревнуются за применение; сервису нужны права DDL |
| **Отдельная команда того же бинарника, до запуска сервиса** | Версия схемы привязана к версии образа; права DDL — только у одноразового шага |
| Отдельный образ с CLI и файлами | То же, но версия миграций и версия сервиса могут разойтись |

## Решение

1. Миграции — SQL-файлы `backend/services/<service>/migrations/NNNNN_описание.sql` в формате
   goose, с обязательной секцией `-- +goose Down`.
2. Файлы встроены в бинарник сервиса (`embed.FS`).
3. Применение — подкоманда: `<service> migrate up` (и `migrate status`), пакет `platform/migrate`.
4. Команда читает `MIGRATE_DATABASE_URL` — строку подключения роли `<service>_migrator`.
   Работающему сервису эта переменная не передаётся.
5. В Compose миграция — отдельный одноразовый контейнер; сервис стартует только после его
   успешного завершения (`service_completed_successfully`).
6. sqlc читает те же файлы как описание схемы: схема для запросов и схема в базе — один источник.
7. Откат (`DownTo`) есть в библиотеке и используется **только в тестах**; в бинарнике его нет.

## Почему так

- Образ сервиса сам знает, какая схема ему нужна: невозможно выкатить код без его миграций.
- Сервис работает под ролью без DDL (ADR-0003) — значит, мигрировать при старте он и не может.
- Один источник для схемы и для генерации запросов исключает их расхождение.
- Каждая миграция проверяется в обе стороны тестом `TestMigrationsApplyAndRollBack`.

## Недостатки

- Откат в рабочей среде не автоматизирован: исправление — новой миграцией вперёд.
- Совместимость миграции с предыдущей версией сервиса обеспечивается дисциплиной
  (expand → migrate → contract), а не инструментом.
- Долгие миграции на больших таблицах требуют ручного планирования.
- goose добавляет зависимости в каждый сервис.

## Условия пересмотра

- Таблицы вырастут настолько, что блокирующие изменения схемы станут заметны → инструменты
  онлайн-миграций и отдельный регламент.
- Потребуется откат в рабочей среде → отдельная защищённая команда и процедура.
