# ADR-0010. Измерение гипотезы: факты в базах сервисов, без сервиса аналитики

Статус: принято · 2026-10-13

## Контекст

MVP — инструмент проверки гипотезы; без данных он бессмыслен (лекция «MVP и ценность», слайды
28, 33, 37). Нужна «минимальная фиксация событий». При этом каждый новый сервис и каждая внешняя
система должны быть обоснованы, а принцип лекции — «автоматизируйте только то, что критично для
эксперимента».

Метрики эксперимента (`MVP_SCOPE.md`): M1 — доля просмотров карточки, закончившихся запросом на
контакт; M2 — доля принятых запросов; M3 — связь доли совпадений с решением; M4 — доля дошедших
до анкеты.

## Альтернативы

| Вариант | Оценка |
|---|---|
| Сервис аналитики, принимающий события от клиентов и сервисов | Четвёртый сервис без пользовательской ответственности; клиентские события ненадёжны и требуют собственного контракта |
| Сторонняя продуктовая аналитика | Передача данных о поведении пользователей третьей стороне; ещё одна интеграция в web и mobile |
| Разбор логов запросов | Логи не предназначены для хранения фактов: нет гарантий полноты и сроков хранения; в логах нет результата сравнения |
| **Каждый сервис хранит факты о собственных действиях в своей базе; сведение — ручная выгрузка** | Никакой новой инфраструктуры; факты записываются сервером в той же транзакции, что и действие |

## Решение

1. Факты записывает **сервер**, в базе сервиса, выполнившего действие. Клиентских событий нет.

| Факт | Сервис | Хранение |
|---|---|---|
| Создание анкеты | Profile | `profile.created_at` |
| Просмотр карточки со сравнением | Matching | `candidate_view`: зритель, кандидат, `matched_count`, `compared_count`, время |
| Запрос на контакт | Interaction | `contact_request`: отправитель, получатель, `created_at` |
| Ответ на запрос | Interaction | `contact_request.status`, `responded_at` |

2. Единственная таблица, созданная только ради измерения, — `candidate_view`. Остальное — данные,
   которые нужны самим сценариям.
3. `candidate_view` сохраняет результат сравнения **на момент просмотра**: анкеты меняются, а для
   M3 важно, что именно видел пользователь.
4. Сведение — вручную: выгрузка из трёх баз и соединение по идентификаторам пользователей во
   внешнем инструменте. Оператор подключается с доступом только на чтение.
5. Качественный сигнал K1 собирается интервью, вне системы.

## Почему так

- Все четыре метрики вычисляются из четырёх фактов; каждый из них сервер и так знает.
- Просмотр карточки = вызов `getCandidate`: отдельного события «посмотрел сравнение» не нужно,
  потому что карточка и есть сравнение.
- Запись факта и действие — одна транзакция одного сервиса: нет потерянных и лишних событий.
- Разовый эксперимент на небольшой группе не оправдывает конвейер аналитики; ручная выгрузка —
  прямое применение принципа «ручные процессы — лучше».

## Недостатки

- Метрики нельзя получить одним запросом: данные в трёх базах.
- Нет событий интерфейса: неизвестно, сколько человек дошло до экрана, но не вызвало операцию;
  нет времени, проведённого на карточке.
- Нет показа карточек в выдаче как факта (только открытия).
- `candidate_view` растёт с каждым просмотром; срок хранения не задан.
- Выгрузка требует доступа человека к персональным данным — нужен регламент.

## Условия пересмотра

- Эксперимент становится постоянным продуктом с регулярной отчётностью → выгрузка в отдельное
  хранилище по расписанию; сервисы не меняются.
- Гипотеза потребует данных о поведении в интерфейсе → отдельное решение о клиентских событиях
  с контрактом и оценкой влияния на приватность.
- Объём `candidate_view` начнёт влиять на базу Matching → срок хранения и секционирование.
