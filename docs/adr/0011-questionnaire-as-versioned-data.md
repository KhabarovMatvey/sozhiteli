# ADR-0011. Анкета привычек — версионируемые данные; обязательные условия — типизированные поля

Статус: принято · 2026-10-13

## Контекст

Анкета состоит из двух разных частей:

- **обязательные условия** (город, бюджет, сроки, предпочтение по полу соседа) — по ним Matching
  фильтрует выдачу запросом к базе;
- **бытовые привычки** — по ним Matching сравнивает двух людей и показывает совпадения.

Состав вопросов о привычках — самая изменчивая часть продукта: формулировки и варианты ответов
не взяты из исследования (в нём их нет), они проверяются экспериментом и будут меняться.
Требование расширяемости: модель профиля должна расширяться без переписывания архитектуры.

## Альтернативы

| Вариант | Оценка |
|---|---|
| Каждый вопрос — типизированное поле контракта (`smoking: enum`, …) | Максимальная строгость типов. Но изменение одного вопроса — это изменение контракта Profile, внутреннего контракта, миграции двух баз, кода Matching и обоих клиентов |
| Всё, включая условия, — свободный JSON | Гибко; но фильтр выдачи по неиндексируемому JSON и отсутствие типов там, где они нужнее всего |
| Конструктор анкет: вопросы в таблицах, редактируются администратором | Гибкость, которая никому не нужна: вопросы меняет команда, а не пользователи |
| **Условия — типизированные поля; привычки — словарь «код вопроса → код варианта» с версией определения** | Строгие типы и индексы там, где фильтруют; свободное изменение там, где сравнивают |

## Решение

1. **Обязательные условия** — отдельные типизированные поля в контракте и отдельные столбцы в
   базах Profile и Matching.
2. **Ответы о привычках** — поле `habits`: объект `{ "<код вопроса>": "<код варианта>" }`, и
   поле `questionnaire_version`.
3. **Определение анкеты** (вопросы, варианты, подписи) принадлежит Profile и хранится в коде:
   `backend/services/profile/internal/questionnaire`. Клиенты получают его операцией
   `getQuestionnaire`.
4. Версии **неизменяемы**. Любое изменение вопроса или варианта — новая версия; `Current()`
   указывает на действующую. Сохранённые ответы ссылаются на свою версию.
5. Profile при сохранении проверяет ответы по определению указанной версии; принимает только
   действующую версию.
6. Matching сравнивает ответы **обобщённо, по кодам**, не зная их смысла: одинаковый код —
   совпадение, разный — различие, вопроса нет у одной из сторон — `not_comparable`.
7. Подписи кодов клиент берёт из `getQuestionnaire`; Matching возвращает только коды.
8. Коды вопросов и вариантов — `[a-z0-9_]{2,32}`; проверяется тестом определения.
9. У каждого вопроса в коде указан код свидетельства из `RESEARCH_EVIDENCE.md`; вопрос без
   обоснования не добавляется.

## Почему так

- Изменение вопроса затрагивает один файл в одном сервисе: ни контракты, ни схема баз, ни код
  Matching, ни клиенты не меняются.
- Условия остаются типизированными и индексируемыми: по ним идёт запрос выдачи.
- Определение в коде, а не в таблицах: изменение проходит ревью и тесты, а проверка ответов не
  требует запроса к базе.
- Неизменяемые версии: люди, заполнившие анкету раньше, остаются сравнимыми по общим вопросам,
  и никакой ответ не меняет смысл задним числом.

## Недостатки

- Типы не защищают коды привычек: опечатка в коде — ошибка времени выполнения, а не компиляции.
- Сравнение только на равенство: «курю на балконе» и «курю дома» — такое же различие, как
  «не курю» и «курю дома». Близость вариантов не учитывается.
- У пользователей с разными версиями анкеты часть вопросов несравнима, пока они не перезаполнят.
- Клиенту нужен дополнительный запрос определения, чтобы подписать коды (кэшируется).
- Подписи только на русском языке; перевод потребует расширения определения.

## Условия пересмотра

- Эксперимент покажет, что нужны веса или близость вариантов → правила сравнения становятся
  частью определения версии; это изменение Matching и, возможно, внутреннего контракта.
- Вопрос станет условием фильтрации (например, «только некурящие») → он переносится в
  типизированные условия отдельным изменением контракта.
- Вопросы начнут меняться чаще, чем выпускается сервис → хранение определения в базе Profile.
- Сегмент 2 потребует другого набора вопросов → несколько определений по типу анкеты.
