# ADR-0012. Межсервисная аутентификация: client credentials и отдельный порт

Статус: принято · 2026-10-13

## Контекст

Внутренний API Profile отдаёт ленту изменений — фактически все анкеты системы. Его должен
вызывать только сервис Matching: ни пользователь, ни посторонний процесс в той же сети.

## Альтернативы

| Вариант | Оценка |
|---|---|
| Только сетевая изоляция | Любой процесс, попавший в сеть сервисов, читает все анкеты; ошибка маршрутизации на edge раскрывает API наружу |
| Общий статический секрет в заголовке | Просто; но секрет бессрочен, одинаков для всех потребителей и не несёт ни срока, ни прав |
| mTLS между сервисами | Надёжно; требует выпуска и ротации сертификатов — отдельная инфраструктура |
| **OAuth2 client credentials через уже существующий Keycloak** | Короткоживущие токены с аудиторией и ролью; проверяются тем же кодом, что и пользовательские; новых компонентов нет |

## Решение

Три независимых барьера:

1. **Отдельный порт.** Внутренний API слушает `INTERNAL_HTTP_ADDR` (`:9080`), публичный —
   `HTTP_ADDR` (`:8080`). Edge маршрутизирует только на 8080; порт 9080 наружу не публикуется.
2. **Отдельная аудитория.** Matching получает токен по client credentials (клиент
   `matching-service`) с аудиторией `sozhiteli-internal`. Пользовательские токены имеют аудиторию
   `sozhiteli-api` и на внутреннем API отклоняются с `401`; сервисные — отклоняются публичными API.
3. **Роль.** Внутренний API требует роль `internal.profile-changes.read`; токен без неё получает `403`.

Реализация: `platform/auth` (`Verifier`, `RequireRole`); в Matching —
`golang.org/x/oauth2/clientcredentials`, который сам получает, кэширует и обновляет токен.
Собственной криптографии нет.

## Почему так

- Используется то, что уже есть: Keycloak и код проверки токенов. Новых компонентов и новых
  механизмов безопасности не появляется.
- Каждый барьер закрывает отказ другого: ошибка в конфигурации edge не открывает API без токена;
  утёкший пользовательский токен не подходит по аудитории; новый сервисный клиент без роли
  ничего не прочтёт.
- Токен живёт минуты, а не вечно; права потребителя видны и меняются в одном месте.

Проверено тестами `TestFeedRejectsCallersWithoutServiceRole` и сквозной проверкой
(`infra:smoke`: внутренний API недоступен через edge; синхронизация с настоящим сервисным
токеном работает).

## Недостатки

- Синхронизация Matching зависит от доступности Keycloak в момент обновления сервисного токена.
- Секрет клиента `matching-service` — долгоживущий; его нужно хранить и менять.
- Трафик внутри сети сервисов не шифруется.
- Роли выдаются вручную в конфигурации realm.

## Условия пересмотра

- Сервисы размещаются на разных узлах или в недоверенной сети → TLS между сервисами, затем mTLS.
- Число внутренних API и потребителей растёт → единый подход к выдаче ролей и, возможно,
  идентификация рабочих нагрузок средствами платформы.
- Требование ротации секретов → хранилище секретов с автоматической сменой.
